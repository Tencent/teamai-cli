# Workflow engine

Maintainer notes on `src/workflow/`. The workflow file format and the driver contract are in the [Workflows](../guide/workflow.md) and [Advanced workflows](../guide/workflow-advanced.md) guide pages.

Each rule below spans more than one file. The rule names the code that owns it, so you can read the details there.

## Workflow first

A feature that orchestrates AI work ships as a default workflow in `workflows/`, which a team replaces with a file of the same name. Its command only starts that workflow, on the driver `workflows.driver` names (`runShortcut`, `driveByDefault`). Only drivers launch AI tools: a feature asks one through an `answer` or `prompt` step, and `teamai/launch-through-workflows` fails an import of the launcher (`src/tool-launch/`), or a process call that runs a tool's executable, outside `src/workflow/`. The engine never branches on a feature: every key a feature needs is generic, and any workflow can use it. Reuse a workflow as a `workflow:` step instead of copying its steps. The rules contributors follow are in [AGENTS.md](../../AGENTS.md#rules) and [CONTRIBUTING.md](../../.github/CONTRIBUTING.md#coding-style).

The features migrated this way, each with the default workflow its command starts:

| Command | Default workflow |
|---|---|
| `teamai import --dir`, `--from-repo`, `--from-repo-list`, `--from-org` | `teamai-import-from-repo`, which runs `teamai-codebase-enrich` and `teamai-codebase-deep-enrich` per repository |
| `teamai codebase --deep-enrich` | `teamai-codebase-deep-enrich` |
| `teamai import --from-tools`, `--from-claude` | `teamai-import-rules`, which runs `teamai-import-learnings` |
| `teamai import --from-iwiki` | `teamai-import-from-iwiki`, which runs `teamai-import-learnings` |
| `teamai import --from-mr` | `teamai-import-from-mr` |
| `teamai ci extract-mr` | `teamai-ci-extract-mr`, which runs `teamai-import-from-mr` |
| `teamai recall maintenance --update-quality` | `teamai-draft-learning-updates` |
| `teamai recall promote <learning>` | `teamai-promote-learning` |
| `teamai score --scorer <file>` | `teamai-try-scorer`; `teamai-new-scorer` drafts a scorer with a person and runs it |
| Recall adoption and skill routing judgments | generated questions of `teamai-score` (`scorers/teamai-adoption.md`, `scorers/teamai-routing.md`) |
| Sharing learnings from earlier sessions | `teamai-share-learnings-from-sessions`, which runs `teamai-share-learnings` |

## Judgment is a scorer

Anything that judges AI work is a scorer, judged by `teamai-score`; no code calls a judge itself. A rubric teamai ships is a default scorer, `scorers/<name>.md` in the package, read by `DefaultScorers` (`src/default-scorers.ts`). It is a template whose variables (`{{ skill.name }}`) `parseTemplate` reads from a set closed per default. Pull caches a team file of a default's name apart from the team's scorers (`syncScorerDefinitions` in `scorers/cache.ts`) only when `DefaultScorers.problems` finds none, with a coded diagnostic otherwise, and `defaultScorerRubric` gives the rubric that fills in: the team's, or the shipped one.

A default whose scorer is asked once per item of a session (a delivered skill, a recalled doc) is a generated question family (`src/scorers/generated-questions.ts`): a name prefix `teamai:<family>:`, the scoring switch that asks its questions, the questions a session has, the one a name names, and what a written label does. Plan, named subjects, the finished-session listing and `score write` go through `GeneratedQuestions` and never name a family. A family pins its filled-in rubric, its variables and any evidence file it adds (`recalled/<hash>.md`) in `pins.json`, so a retry judges what plan saw. Adoption's `written` credits votes once per root session and doc through the recall log (`creditAdoptionVerdicts`); routing has none.

## Rules that span files

- **A run ends only in `settleRun`.** The shared `finishRun` path calls it when settling reaches the top workflow's result, before it hands any lease back or out, and on a call that takes no lease too. `reportAttempt` first reconciles earlier reports, so an end cancels a later report before it can advance the revision. It records an accepted outcome and never ends the run. After a failed report, the next `next` skips the dependents and ends the run. Respond, cancel and retry in `run-controls.ts`, and next in `engine.ts`, share that path. Whole-run cancel settles directly as `cancelled`, without reconciling another round. A run whose workflow declares `finally` does not end there: after any judge wait, `finishRun` freezes the verdicts, then calls `enterFinalizing`, which keeps the run `running`, holds the outcome in `finalizing` with `until` as the run's deadline, and adds the `finally` instances; `reconcileRun` then settles `finallyScope` instead of `topScope`, and `settleRun` ends the run with the held outcome, whatever the `finally` steps did. To run code when a run ends, hook into `finishRun`. Do network I/O only after `withRun` releases the run lock. That path queues the end record, a local write, under the lock, and saves whether it did in the run's `endRecordQueued` field. When `updateRun` then fails to save the run file, the queue is one save ahead of the run file, and the next `next` settles the run again and overwrites the queued `<run>.end.json`. A later `next` reports a record state only for a run whose field is true (`runRecordState` in `records.ts`).
- **Reconcile the latest report before applying another or handing out a lease.** `reconcileRun`, shared by `leaseNext` and `reportAttempt`, settles every driverless transition to a fixpoint at the run's current revision, through `settleScope` and `settleItems`, including workflow starts, fan-out expansion, render failures and bound exhaustion. `reportAttempt` advances the revision only after it, so only the latest revision can be unreconciled. A reached end applies before a loop decision. Only after reconciliation does `leaseNext` hand back an omitted open lease or issue the first ready leaf in declaration order that this driver can take. A running workflow occupies its parent's position in that order. Settling returns every ready leaf in that order (`ready`), and `leaseNext` walks it. A ready item does not count against `max_parallel` until it is leased, and one `next` leases at most one step, so a held-back item leaves its room to the next one without exceeding the cap. `canTakeLease: false` still reconciles driverless transitions. Every changed run is saved, including a `wait`.
- **A report is checked against the revision of its own lease.** `reportAttempt` and `retryStep` increment `revision`; skips, `if`, `end`, and the creation of child steps inside `next` never do. A lease keeps the run revision it was handed out at, and `reportAttempt` compares a report with that, so the report of a parallel lease does not make it stale. An attempt that is not an open lease keeps the older answers: `stale_revision` when its revision is not the run's, otherwise `wrong_attempt`.
- **An end or break stops what is still open under its workflow.** `stopWhere` cancels every leased step under the workflow that reached the end, its sub-workflows included, and keeps the attempt on the step and in `cancelledAttempts`. It cancels running workflow steps there and skips pending and waiting ones; while the run's `finally` steps run, where only a whole-run cancel or the deadline reaches it, it cancels those too. The walk takes a path predicate and failure. End and break construct their own end_reached failure; manual cancel and retry supply theirs. Step descendants use the same `isUnder` predicate as `archiveUnder` in `loop.ts`. A cancelled delivering step keeps its agent settlement and its original `settledAt` for explicit recovery, records and scoring. Automatic delivery and workflow-item branch summaries exclude cancelled children. Cancel records the ids this walk changed before reconciliation can settle or skip other steps. `reportAttempt` answers a cancelled attempt `lease_cancelled` before it checks the driver; `cancelledAttempts` is never trimmed. Every `next` answer lists in `cancelled` the attempts the driver says it runs that are no longer its open leases, so the driver learns of a cancellation from any answer, `done` included.
- **The local driver overlaps steps that do not share a checkout.** `runLocalDriver` runs up to `workflows.max_parallel` steps (local config, default 1) and sends the ones it has started as `running`. With none set it passes `isOneAtATime` to `leaseNext`, which then leases a step beside the open leases only where `runsBeside` in `engine.ts` allows: two items of one `for_each` that declares `max_parallel`, which `startedItems` bounds. A run whose definitions, admitted ones included, declare such a `for_each` (`mayRunItemsBeside`) then runs with no count of its own and the signal policy of `max_parallel` above 1; any other run keeps 1. A workflow a `from` step admits counts only once the run is driven again. Other drivers do not pass `isOneAtATime`, so `next` leases them ready steps side by side as before. A command with no workspace, and a prompt in the current checkout, share that checkout, so only one of them runs there at a time. A prompt earlier in the queue for that checkout blocks a later command there. The driver lists the leases it has not started in `queued` and takes the deadlines the answer gives them, so waiting for the checkout does not use up a timeout. The driver starts the prompt when the checkout is free and fewer than `max_parallel` steps are in flight; commands in other worktrees keep running. A prompt with its own worktree does not take the checkout, nor does an answer with one. Outside a git work tree no snapshot can check an answer, so there an answer takes no place (`placeOfLease`). A headless prompt takes one of the slots, and the driver keeps leasing steps for the others while it runs. An interactive prompt uses the terminal, starts only when no command is running, and no step is leased while it runs. On `cancelled`, it drops a held lease, and it stops a running command with SIGTERM, then SIGKILL after 5 s while any captured descendant or process in a detached group remains, even after its command exited. Attached commands snapshot their descendant tree and start times before stopping, then probe and send SIGKILL only to descendants whose start times still match. If the identity snapshot fails, only the shell is stopped; detached commands use their process group. It does not send a stopping command as `running` again, so `next` does not cancel it twice. Dying commands still take a slot, and a new attempt of their step waits until they are gone. The signal policy follows `max_parallel`. At 1, a command runs in teamai's process group, as `env exec` runs one (`src/env-exec.ts`): the terminal's Ctrl-C reaches it, and it can read `/dev/tty`. A signal `env exec` would pass on (SIGTERM or SIGHUP, and SIGINT or SIGQUIT when the terminal does not reach the command) makes the driver stop the command, wait for it, and exit with that signal. Above 1, each command runs detached in a process group of its own, recorded in the attempt's `group-<pid>.json` as setup's is, with no terminal, and SIGINT, SIGQUIT, SIGTERM or SIGHUP makes the driver stop every group, wait for them, and exit with that signal. Windows uses `taskkill /T /F` in place of the group kill. Staging runs inside the attempt at every `max_parallel` (`stageThenStart`), so the driver keeps polling while it stages, and a cancel aborts staging. A step whose attempt was cancelled, or whose lease expired, while it staged never starts. `runPlaceSetup` in `place/place.ts` runs setup (`setup.ts`) after the git phase, only in a worktree prepare just created, with setup's own keys, and removes the worktree when setup fails. It records `setting-up` before setup starts, and a prepare that finds that phase gives the place up as a failed setup does, so a second setup is never checked against what one cut short left there. Before it stages an attempt the engine hands back, the driver stops every group a killed driver's setup or command left there (`stopRecordedGroup`), each recorded in the attempt's own `group-<pid>.json`.
- **An answer step reserves the checkout read-only, on every driver, unless it asks for a worktree of its own.** `resolveMode` and `planWorkspace` in `workspace.ts` give it read-only with no separate workspace contract. With `workspace: new`, `planAnswerCopy` gives it a read-only contract on a branch of its own at the run's base, so prepare opens a reader copy (`stageRole`) with no team overlay (`overlaid`), finish checks and puts it back (`leaveReadCopy`), and the accepted success removes it; a run with no base reads the checkout instead. `leaseData` marks its lease `answer: true`, with the rendered prompt and no session. `placeLeased` in `protocol.ts` prepares the usual checkout reader, which holds the checkout until its report checks and finishes it. The local driver stages it the same way and runs `runAnswerStep` (`drivers/local/answer-step.ts`) through `createToolCaller`, using the member's tool ladder and `call` launch, launched by `answer`. Answers in the checkout share it with commands, so `placesBusy` serializes them, even across fan-out items. Pull keeps its keys to `ANSWER_STEP_KEYS` in `parse.ts`, and its `workspace` to `new`.
- **`writes` narrows `read_only_dirty` and never opens a place.** Pull checks each path as written (`Writes.isCheckoutPath` in `writes.ts`), and `writesTemplateErrors` keeps its templates to inputs. `renderLease` checks the rendered list again (`Writes.isRenderedPath`: inside the checkout, or absolute) and fails `invalid_template`. The list goes on the lease, into the place record (`PlaceFields.writes`) and to `finishReader` in `place/reader.ts`, which makes each absolute path relative to the checkout, drops one outside it (`Writes.inCheckout`: nothing there can dirty the checkout), then drops a changed path under the rest before deciding `read_only_dirty`. A HEAD move is kept only as commits added on the branch the step found, each path they change under the rest (`isCommitUnder`), so a command can publish what it wrote when the checkout is the repo it publishes; a switch, a detach or a reset never is.
- **Progress lines are a report field.** `parseReport` keeps the last `PROGRESS_LINES` of a report's `progress` on the pass, `doneData` answers them per step with the run's end, and the snapshot drops them. The local driver reports a command's stderr lines as progress, masked, and shows each one as it comes to `LocalDriverOptions.progress`.
- **An input's default is filled in before the inputs are checked.** `defaults.inputs` (`parseDefaultInputs` in `parse.ts`) holds a value of an input the file declares, of its type. `withInputDefaults` in `engine.ts` fills each input a start (`startRun`) or a step's `with` (`startWorkflowStep`) leaves out, so the run state and a step's `inputs` hold the value used, and `inputsMismatch` still requires every declared input. Pull's `with` checks (`referenceDiagnostics` in `parse.ts`, `withMismatch` in `cache.ts`) let a step leave a defaulted input out. A cached definition from before the key has no `defaults.inputs`, so every input it declares stays required. Add an input to a workflow other workflows run with a default, or every caller breaks at pull.
- **A feature command starts its workflow through `runShortcut` in `workflow-commands.ts`.** It checks that a team file of the default's name takes the inputs the command gives, starts the run on the driver `driveByDefault` picks, shows the run's progress lines on the stream each was meant for (`PROGRESS_STREAMS_ENV` in `utils/logger.ts`), prints `outputs.text` and exits with `outputs.exit_code`, or 1 when the run did not succeed, and prints the envelope instead under `--json`. It names the run only when the run is still open as it stops driving it, interrupted or waiting on a person, with `Run <id> is still open. Continue it with: teamai workflow resume <id>` (`resumeWhileOpen`); `workflow start` names it as it starts. `explainFailedSteps` says why each failed step failed, once with a count and the step ids for steps that failed with the same code and message. A private run starts no drain, and neither does a run inside a workflow step (`nestedCall`), private or not, since a team's copy of a default may drop `private`. A run that asks a person before it writes anything passes `nobodyAnswers`, which is said, exit 1, before the start when `personAnswers` is false, so an import inside a workflow step fails at once instead of waiting on a question nobody sees.
- **A released command keeps working wherever it ran before it became a shortcut.** The person or agent asked for the command, not the workflow, so `runShortcut` starts with `asCli` (`ShortcutStart`): no agent evidence, so neither `invoke` nor the nested-start checks judge it, and an agent's start is recorded as `startedBy: 'cli'` through `startAsCli`. Inside a workflow attempt (`nestedCall`), the shortcut drives its run on the local driver in its own process, whatever `workflows.driver` says, so the step that runs the command owns that run: its lease, place and timeout govern it, and the step ends when the run does. Naming the workflow is still judged: from an agent session, `teamai recall maintenance --update-quality` runs, and `teamai workflow start teamai-draft-learning-updates` answers `invoke_denied`. Never key this on a workflow name.

  ```yaml
  # workflows/weekly-quality.yaml: the step drives teamai-draft-learning-updates to its end
  schemaVersion: v1alpha1
  name: weekly-quality
  description: Draft updates of the entries the team recalls often but rarely adopts.
  steps:
    - id: drafts
      command: teamai recall maintenance --update-quality
  ```
- **A workspace is a git contract on the lease. TeamAI owns the workspace contract and its git; the host owns the place. TeamAI reads the delivered commit and opens the PR outside the run lock.** `place/` prepares and finishes every place: the local driver prepares through `place.ts` in process, and `next --prepare` through `protocol.ts` for a driver that runs the protocol from the CLI; every driver's report finishes and releases its place through `managedReport` in `protocol.ts`. `preparePlace` records each place in `attempts/<attempt>/place.json` by phase (`opening`, `preparing`, `staged`, `setting-up`, `ready`, `finished`, `abandoned`), with the reader's snapshot in `before.json` and the branch's agent files in `overlay/` beside it, so whichever process reports the attempt finishes it. It records `opening` before git touches the copy, with whether the copy existed and, once it is open, a writer's range start, taken before any merge, so a prepare killed in git is finished by the next prepare of the attempt, which still runs setup in a copy the killed one created and keeps its merges in the step's `changes`. It records `preparing` before it touches the agent files, and copies them aside to `overlay.partial/`, renamed to `overlay/` once complete, so a prepare killed during the overlay is finished by the next prepare of the attempt, or put back by `abandonPlace`. `next --prepare` leases and prepares under the run lock, and a prepare that fails settles the attempt `failed` with its own code. `report` refuses caller `changes` and `read` for a prepared attempt, finishes its place before it reports, and leaves the place as prepare found it (`abandonPlace`) when the attempt is `released` or the run answers `lease_cancelled`. `planWorkspace` in `workspace.ts` chooses the mode. An explicit `workspace` wins. A command that omits it is read-only, even inside a copy; when it exits 0 and changed the checkout, the driver fails it `read_only_dirty`. That includes a commit that leaves the worktree clean, a switch to another branch or a detach at the same commit, a change that only stages an existing edit, another staged hunk that leaves the status mixed, a permission change on a file that was already dirty, an edit to a quoted non-ASCII path, a symlink whose target changes while the file it names stays the same, and an edit to the destination of a staged rename, and a change inside a submodule that was already dirty. An interactive prompt that sets `workspace: read-only` is checked the same way. An interactive prompt that does not may change the checkout, and those edits stay. Conflict paths, including agent files, are read without Git's quoting, so a non-ASCII name is still checked for leftover markers. A prompt that omits it continues the nearest enclosing `new` or `continue` workflow, and a `for_each` ancestor makes that `new`, so items do not share a worktree. A workflow whose header says `workspace: new` works in one copy: started on its own, the run opens it, and every chain of levels to a step starts with that copy (`runLevels`, told apart by `isRunLevel`). Every chain grows through `levelsInside`, which makes a step with no `workspace` that runs such a workflow open a copy, as `workspace: new` on it would, unless a copy is already around it, which the workflow's steps then continue. `levelsTo` builds the chain to a step instance at lease, and `deliveryProblem`, `describeWorkflow` and the role checks in `parse-roles.ts` walk the tree with it. `leaseNext` puts the contract on the lease for `new` and `continue`, and for a read-only step inside a copy (`mode: 'read-only'`, `merge: []`). That reader's branch is the one its declared `needs` wrote or read (`changes` or `read`, through items and children, but not `after` items or inherited needs), or the enclosing copy's when they touched none; needs on several branches fail `workspace_base`. It needs `continue` in `can.workspace` and the copy's owner, as `continue` does. A read-only step outside any copy gets no contract and runs in the active checkout. A step whose `workspace` is `clone: { commit, repo?, team }` opens a clone (`place/clone.ts`), which needs `clone` in `can.workspace` and `next --prepare`: `preparePlace` makes a fresh clone of that commit outside the checkout, with its own `.git`, no remotes and hooks off, and installs the team under the clone's own HOME. The steps inside it that `continue` run there, their commits stay in the clone, and `sweepClones` removes it once nothing in it is still to settle. A step whose `workspace` is `{ team: { branch? } }` runs in a fresh clone of the team repo (`place/team.ts`), on the local driver and on the skill driver's hosts h1 to h3, whose runner has teamai prepare it (`team` in `HOST_PROFILES`; h4 offers none): `openTeamClone` clones origin with the member checkout's credentials and goes on from the branch with the default branch merged in, `finishTeamClone` refuses a commit `teamai pull` would not place or would newly reject (`rejectedTeamFiles` compares `review-branch` against the default branch) and pushes with a lease on the tip it found, and `deliver: pr` opens its PR into the team repo's default branch. It runs with no role (`copyOf` gives it no copy), its run is not published (`worksInTeam`), and `sweepClones` removes its clone once the run is not running. With `deliver: publish` on a teamai data branch (`teamai-reports` or `teamai-learnings`, `DATA_BRANCHES` in `types.ts`), the step runs instead in a detached checkout of origin's tip of that branch (`place/data.ts`, the `data` role), with nothing merged in. `finishDataCheckout` refuses a staged path outside the member's own directory or file (`scores/<member>/…`, `votes/<member>.yaml`) and any deletion, then applies what the step staged to this machine's persistent checkout of the branch under its lock (`DataBranches` in `utils/data-branches.ts`) and pushes. A push origin cannot take leaves the commit there, and the step succeeds with a pending message; the next `teamai pull`, `teamai score --push` or `teamai score --drain` sends it (`DataBranches.pushPending`). The kept patches of a branch are one queue: every publish keeps the step's patch under `<dataHome>/data-branches/<branch>/pending/` (`DataBranches.keep`), and `DataBranches.send` commits the queue to the persistent checkout under its lock, oldest first, one commit per patch, removing each patch once it is committed, so a busy lock or a conflict loses nothing. `openDataCheckout` starts the step at that checkout's unpushed commits when they hold origin's tip, and applies the queue on top, so what the step stages is cut after the data still pending here. `pushPending` sends the queue the same way, and drops a patch that does not apply but whose reverse does (`git apply --check --reverse`), which is already on the branch in its own context. One that only appends lines at the end of its files and does not apply is appended to those files as they are, since another step appended there after it was cut. Such a step is neither a copy nor a team role, so its run can be published. In an isolated run, `skipUnreachable` skips it once it is ready, with a `message` that says so, since the run's data stays off the team's anyway; no driver then needs `team` in `can.workspace` for it. A run whose definition opens a clone, or runs a `from` step, is isolated (`isIsolated`): its records say `isolated: true`, and it is not published, claimed, retried, or counted in member stats. `preparePlace` stages it there as a reader, and `finishPlace` checks it; a second prepare or finish returns the first one's result. `place/reader.ts` stages a reader in a copy without merges, takes its snapshot over the base overlay, and afterwards restores the overlay; when the step changed the copy or left its branch, it keeps the state on `refs/teamai/kept/<attempt>` (`git add -A`, then `write-tree` and `commit-tree` on HEAD; not the stash list, which every worktree shares), and pushes each submodule commit that tree records and the read commit does not into the checkout's git dir as `refs/teamai/kept-modules/<attempt>/<commit>` (at any depth, without the user's push hooks or `push.recurseSubmodules`), since a gitlink does not keep its commit reachable once the copy is removed, then runs `git checkout -f <branch>`, `git reset --hard` to the commit it read, `git clean -fd`, and `git submodule update --checkout --recursive` on the submodules it changed, so a later writer never commits a reader's edits. It resets nothing when a repository among the changed paths has uncommitted or untracked files, or a nested submodule commit its parent does not record, which the keep cannot hold. The copy counts as put back only when HEAD is `refs/heads/<branch>` at that commit and `git status --porcelain --untracked-files=all --ignore-submodules=none` prints the same lines it printed when the reader was staged; ignored files are left in place. Otherwise the reader fails `workspace_base`. `preparePlace` writes a `teamai-unrestored` marker, with that status, in the worktree's git dir before the reader's overlay, and the driver removes it once the copy is put back or left untouched, so a driver killed mid-reader still leaves it. `openWorktree` in `place/created.ts` refuses later leases in a marked copy until the copy is back, when it removes the marker. A status line does not show content, so a marker whose status was not empty stays until the person who puts the copy back deletes it. `ensureWorktree` also refuses an existing worktree whose HEAD is not on its branch or a directory that is not a worktree, and prunes and recreates one whose directory was deleted. Parallel steps run git in one repository, and git writes a new worktree's entry without a lock, so a command that reads every worktree (`fetch`, `branch`, `worktree add`) beside it dies on the entry half written (`failed to read .git/worktrees/<id>/commondir`). `git` in `worktree.ts` runs such a command again, and `ensureWorktree` makes the branch before `worktree add`: `worktree add -b` makes it before it reads the worktrees, and would find it made when it ran again. The reader reports `read` (`branch`, `base`, `commit`) and never `changes`. `report` returns `invalid_report` for `read` on any other lease, and for `changes` or a success without `read` on a reader's lease. `run.copies[].commit` and fan-out `branches` follow `changes` only. `cleanup` comes from the lease's contract, so a reader that was the copy's last user removes it too. `leaseNext` holds a step back for this driver, and tries the next ready leaf, when the driver's `can.workspace` lacks that mode, or when a `continue` copy belongs to another driver (`run.copies`). It answers `wait`, with every held step's reason joined by `; `, only when every ready leaf is held back. Driver capabilities stay out of `reconcileRun`, which `reportAttempt` and the run controls also call. It fails `workspace_base` when `continue` has no enclosing `new`, or when the run has no base. `workflow start` in a git checkout records the base (commit, and the branch unless HEAD is detached); otherwise the first `next` that sends `base` sets it, and a later `base` never changes it. The local driver fails a lease whose `workspace` it cannot read with `workspace_base` instead of running it in the active checkout. The branch is `teamai/<runId>/<path-safe step path>/p<pass>` (`branchName`); a `[n]` in the path becomes `-n`. The run's own copy is on `teamai/<runId>/_run` (`runCopyBranch`), which no step path takes. `next` does not name it: when a succeeded run left commits there, `workflow start` and `resume` with the local driver, and the skill driver at D16, read it from the run file (`runCopyToMerge`) and name it with its `git merge` line. The first branch in `needs` order is where the step starts, and the rest are merged in that order. An item's `after` branches come first. `place/` (`created.ts`, `overlay.ts`, `worktree.ts`) adds the worktree under `.teamai/workflow-worktrees/` of the checkout the run started from (`run.checkout`), or of the driver's own checkout when it does not share that checkout's git directory, such as a separate clone (`placeRoot`), points `core.hooksPath` at an empty directory, and replaces `AGENT_PATHS` (`AGENTS.md`, `CLAUDE.md`, `.agents`, `.githooks`, and each default `toolPaths` entry's project directory, project MCP file and Copilot `.github` paths) with the run's base commit. An agent path under a symlinked parent fails `base_config` before anything is copied or removed, since both would follow the link. It then gives the worktree the inline `pull` a new worktree gets (`prepareCheckout`), which delivers the team's skills, rules, agents and MCP and records that checkout's team revision. The overlay is taken after that delivery, so those files are not the step's commit. A path the step edits is committed. A step that left HEAD off the leased branch fails `workspace_base` before anything is committed, reported as `changes`, or pushed, and the worktree stays as it left it. A path it leaves untouched is put back from the branch. A merge conflict stops the merge: a command fails `merge_conflict`, and a prompt is told the branches that remain. Snapshots and commits read submodules with `--ignore-submodules=none`, and after `git add -A`, which skips a submodule whose `ignore` is `all`, each submodule is staged by name, so `submodule.<name>.ignore` and `diff.ignoreSubmodules` hide no change from a reader's check, its keep, or a writer's commit. The driver commits as `TeamAI <teamai@localhost>` and reports `changes` (`branch`, `base`, `from`, `to`, `commits`). It pushes when `origin` exists and this step made commits, whether the step succeeded or failed, and also when a later attempt adds no commit but this branch has commits `origin` does not have, including a first push that never landed and an origin with no tracking refs yet. A failed push fails a step that succeeded with `push_failed`, and the worktree stays. `report` sets `cleanup` only when the step succeeded and no step that can still run uses that branch, judged on the run as the next `next` settles it: steps a loop runs again count, and a workflow or `for_each` step that has not started counts by the branch `plannedBranch` gives, the one around it unless it opens its own; only then does `releasePlace` run `git worktree remove --force`. It does not delete the branch, and it never resets, cleans, or switches the active checkout. A command that starts its own sandbox, such as `docker`, stays read-only. What it writes does not feed `new`, `branches`, or a later step. `session: continue` and `session.from` are step reads. The engine puts `{ tool, id }` on the lease, with `earlier`, the sessions that one continued, newest first, and never copies a session. The driver resumes Claude and Codex by that id, copies another tool through `AgentSession.copy`, restores a copy from the team session archive when neither works, and tries each `earlier` session the same way before it starts fresh. OpenCode has no resume flag, so it starts fresh. A driver that continued the lease's session or an earlier one, by that id or in a copy, echoes the one it continued as `resumed` in its report. One that started a new session leaves `resumed` out. `reportAttempt` answers `invalid_report` for a `resumed` on a step that resumes no session, and for one that no pass of the run reported and no link continued (`knowsSession`). When the reported `tool` and `session` differ from `resumed`, `reportAttempt` appends `{ from: resumed, to }` to `run.sessionContinuations`. `sessionOf` follows those links from the session a step would resume, taking the latest link from each session, so a later step resumes the copy that holds the last turns, whichever machine or tool made it. The snapshot publishes the links, so `resumableSessions` on this machine and the claim on the next one both see them. A step that resumed by the same id adds no link, so a run on one machine with one tool leases the same sessions as without links.
- **Only teamai delivers a step's team role, into a copy it prepared, and only teamai records it.** `stepRoleOf` in `workspace.ts` answers the role a step runs with: the role of the copy it runs in (`copyOf`), which the step opening that copy resolves (`resolvedRoleOf`: its own `role`, else the nearest enclosing `workflow` step's, else the nearest file's `defaults.role`). - **A driver pushes the commits it reports, and fetches the commits it is leased.** Every driver keeps these two git rules, so a run another driver or another machine continues finds each commit on `origin`. Whenever `origin` exists, a driver pushes the commits it reports in `changes` before it reports them, failed steps included; `finishWriter` in `place/writer.ts` pushes for every outcome. A push that fails still reports the commits. A step that succeeded fails `push_failed`. A step that failed keeps its own failure, and the push sentence is added to its message: a retry must fix the step first, and a `push_failed` in its place would hide that cause from the person and from the run record. Before it starts from, merges, or applies a lease commit (`start`, each `merge[]` entry, `configCommit`), a driver checks it with `git cat-file -e <c>^{commit}`. For a missing one it fetches `+refs/heads/teamai/<run>/*:refs/remotes/origin/teamai/<run>/*`, and checks again, since a refspec fetch that matches no branch exits 0. A fetch by commit id is not used: a server can refuse it, and a fetched commit no ref holds can be collected later. A commit still missing fails `workspace_base` naming the commit and its branch, before anything merges or runs, so it is never a file-less `merge_conflict` or a prompt told to resolve one. `openWorktree` in `place/created.ts` does this through `fetchMissingCommits`, for the local driver and for `next --prepare`, and `adoptedMismatch` in `place/adopted.ts` for a place the host made. `workflowGitConformanceScenarios` in `conformance/git.ts` checks both rules against a bare origin, and `workflow-git-conformance.test.ts` runs them against the local driver.
- **`next` delivers pull requests, outside the run lock.** A `deliver: pr` step whose agent succeeded becomes `delivering` (`startDelivery`), holding `delivery` (`branch`, `head`, and a kept `reported` URL). It is neither `stopped()` nor `settled()`, so dependents wait, and `startedItems` does not count it, since `max_parallel` bounds agents. Every `leaseNext` calls `drainDeliveries` after an optional claim and before its locked body, whichever driver called it. The drain takes `deliveryLockPath` once; while another process of this machine holds it, the call delivers nothing and `next` answers `wait.delivering`, which the local driver polls. Each round picks a job under the run lock (`nextDelivery`, then `unresolvedCreate` in `delivery-ledger.ts`), runs `deliverPr` or `findDelivered` in `pr-delivery.ts` with no lock held, and applies the outcome under the run lock with `completeDelivery` or `resolveCreate`, which read the immutable job rather than the step. `deliverPr` requires origin's tip of the branch (`ls-remote`) to be the reported head or the latest `copies[branch].commit` a report recorded, and a recorded later tip to contain the reported head (`merge-base --is-ancestor`), else `branch_rewritten`. A tip past the recorded commit that still contains it is `branch_ahead`. `completeDelivery` keeps the step `delivering` while a step that writes the branch is leased (`branchWriterLeased` in `engine.ts`), since that step may push before it reports, or when `copies[branch].commit` is no longer the job's `recordedHead`, since a report recorded a commit while the drain read the branch. The drain does not pick it again in that call. Otherwise no report of that tip can come, and the step fails at once with the `branch_ahead` message, which says the tip holds the checked changes and later ones no report recorded. The same two conditions hold back a pull request: the step stays `delivering`, and one the job found or was told of gets no receipt, while one it opened does. The `branch_moved` and `branch_missing` remedies name the recorded commit. `deliverPr` fetches and diffs the selected tip against the run base on the run's checkout, running every git call that reaches origin within `DELIVERY_TIMEOUT_MS` and with `NON_INTERACTIVE_GIT_ENV`, and rejects protected paths (`protectedPaths` in `worktree.ts`: `AGENT_PATHS` plus `DELIVERY_ONLY_PATHS`) before it accepts a reported URL, looks up or creates. When a recorded later tip changes protected paths, it also diffs the step's own head: a clean own head is `later_protected_path`, a `delivery_failed` that names the later commit, so a retry delivers again instead of running the agent. Its remedies are the ones the run accepts: put origin back at the step's own head, or retry the workflow step whose copy the branch is (the job's `openedBy`). The job of a workflow step carries `childWork` (`childWorkOff` in `workspace.ts`): the head of each step inside it that succeeded on another branch that no step inside it delivers. Each must be an ancestor of the tip, else `child_work_left_out`, since the pull request would leave that work out. A workflow step whose branch holds nothing beyond the run base opens no pull request, so `finishStep` fails it with the same message when such work exists (`workLeftUndelivered`). It looks the branch up before the create and again after it, and reads origin's tip again between that first lookup and the gate. Only a lookup's URL is ever recorded. A post-create lookup that fails, or that finds none after a create that answered, fails delivery with `create_unconfirmed` and keeps the unresolved entry for a later lookup. It treats a found URL on another host than the origin's pull requests as a fault. Its gate, `markCreating`, takes the run lock right before the create: it reconciles, refuses unless the same pass of the same commit still delivers, answers `busy` when `copies[branch].commit` is no longer the job's `recordedHead` or while a step that writes the branch is leased (`branchWriterLeased`), and lists the request in `run.creating`. `nextDelivery` passes over a step while a step that writes its branch is leased (`branchWriterLeased`), so no git or provider call runs for it, and no reported URL or found request is accepted, until that step's commit can be checked. The gate's check covers a lease granted while the delivery runs. Timeouts (`expire` in `limits.ts`) and budgets settle in `reconcileRun`, which both `nextDelivery` and this gate apply, so no delivery is looked up, opened or accepted once a limit stops the step or the run. A new condition that stops a run belongs there too. A run lock it cannot take is `busy` too, as is a tip that moved during the lookup, and neither is a refusal: nothing is listed or opened, the step stays `delivering`, and the drain stops for that call, so the next one checks the branch again. A new receipt on a run that already ended queues the end record under the run lock, and it publishes after the drain releases the delivery lock. In `reportAttempt`, the lookup that vets a reported `changes.pr_url` (`reportedPrMismatch`) is the only delivery I/O, and it runs before the run lock. On the origin's host, a lookup that fails or answers an unsafe URL drops the reported URL. No provider code merges; `teamai/no-provider-merge` enforces this in `src/providers/**` and delivery.
- **A pull request is reused by provider lookup, never by a stored receipt.** `delivery-schema.ts` owns the schemas of delivery receipts and unresolved creates, and `CommitIdSchema`. It imports only `zod` and `pr-url.ts`, so `snapshot.ts` and the run store load no delivery code or provider, which `teamai/workflow-boundaries` checks through the runtime dependency graph. `delivery-ledger.ts` owns their pure updates. The engine passes `reconcileRun` into the ledger and keeps the drain and create gate. Three fields keep what delivery did. `run.deliveries` is an append-only receipt list, deduplicated by URL, that only `recordReceipt` writes, for `completeDelivery` and `resolveCreate`. `deliveryTarget` in `workspace.ts` reads which branches delivered, `buildEndRecord` in `records.ts` reads it as `prs` in list order, and the snapshot publishes it. `copies[].from` is the branch a copy grew from: `rememberCopy` writes it once, at the copy's first lease, from the contract `planWorkspace` ordered (`after`, then `needs`, then inherited needs), before the copy has a commit. `deliveryTarget` walks it to the nearest branch with a receipt, else `run.base.ref`, and the snapshot publishes it and refuses one outside `teamai/<run>/`. `run.creating` lists each request TeamAI asked a host to open and holds no receipt for. `markCreating` appends it, `completeDelivery` removes it with the receipt of a delivered outcome and keeps it on a failed one, and `resolveCreate` applies a lookup of it: found appends the receipt and removes it, unsafe removes it immediately, and none or failed removes it after its second none or third failed answer. Each entry keeps total, none and failed lookup counts in `lookups`, set to zero by the gate each time it opens, including for a request listed before, and advanced only by `resolveCreate`. `unresolvedCreate` picks each at most once per drain, never in the drain that created or failed it, after the delivering steps, in an ended run too, and `findDelivered` reads only the origin and `findOpen`. It touches no step, so a retry, cancel or archive cannot lose the request, and a lookup cannot settle or fail a step. A delivering step whose request is listed still looks up before it creates again. The snapshot publishes the list, so a claimer looks the requests up.
- **What an attempt's own commands deliver reaches its pass only through `runs/<run>/outcomes/<attempt>.jsonl`.** `appendAttemptOutcome` in `store.ts` is its only writer, called by `contribute` when `ATTEMPT_ENV` names the attempt and the run is in its scope. `reportAttempt` reads it with `readAttemptOutcomes` once the attempt has ended, for every driver, and keeps it as the pass's `outcomes`. `buildEndRecord` publishes a pass's `outcomes` as its commits, its delivery receipt, then those, each once. An attempt that ends without a report, such as one whose lease expired, keeps none.
- **A succeeded run deletes its branches only after its end is on origin.** `cleanUpSucceededRun` in `leftovers.ts` runs after `publishRunEnd`, from `leaseNext` and `controlRun`, and takes its result: a publish of a running run checks that origin holds each copy's branch (`checkOrigin`), so a branch deleted first would fail it. When the end did not publish (`notPublished` set) it deletes nothing and warns that the run's branches stay, unless another install owns the run. It keeps the branches of pull requests (`pullRequestBranches` in `records.ts`, also the end record's `prBranches`) and the final copy (`runCopyToMerge` when it names one, so cleanup and the driver's `done` name the same branch), deletes the others once a kept branch contains their tips or they are at the run's base, as the base pin and an answer's copy are, and writes what it did to `RunState.leftovers` at the run's revision. Every deletion is bound to the tip it examined (`--force-with-lease=refs/heads/<branch>:<tip>` on origin, `update-ref -d refs/heads/<branch> <tip>` here), so a branch another machine moved stays, as a failure. It runs again only for a later revision or a failed deletion, which `doctor --fix` retries. It reads the run and deletes under the run's cleanup lock (`withCleanupLock` in `store.ts`, taken without waiting, never the run lock), which `retryStep` holds while it prepares and changes the run (`controlRun`'s `reopen`): a retry answers `busy` while a cleanup deletes, and a cleanup that finds the lock held deletes nothing, for `doctor --fix` to retry. **A retry brings back what a success cleanup deleted before it reopens the run.** Under that lock and outside the run lock, a retry of a succeeded run first runs the retry's own checks on the run as read (`retryRefusal`, `retryTarget`), so a retry refused anyway changes nothing, then `restoreRecordedBranches` reconciles the branch of each copy of the checkout the run recorded (`copies[<branch>].commit`, not `kind: clone` or `kind: team`) with the tips here and on origin. It does not go by `leftovers`, which list only deletions that went through on both sides and which a snapshot drops, so a branch deleted on origin only, or a run claimed after its cleanup, is brought back too. It runs in the driver's workspace, else the run's `checkout`, which a claim sets. The base pin is not restored: a publish pushes it again (`checkOrigin`). A missing branch is recreated at its commit, on origin with an empty lease (`--force-with-lease=refs/heads/<branch>:`, after fetching a commit the checkout lacks from the kept branch that holds it) and here with `update-ref refs/heads/<branch> <commit> ''`. A branch already at that commit is left; one at another commit, on either side, is not moved. Any branch not back answers `branches_not_restored` naming it and why, and the run stays settled. The reopen drops `leftovers`, so the next end cleans up again. Running it again after it stopped midway ends the same. `sweepLeftovers` is the only other remover. **A settled run is never reopened past its `retainedUntil`, and no install removes what a run left before then.** `finishRun` sets `retainedUntil` (settle time plus the owner's `workflows.retention`, absent under `never`) on the run's first settle only, which the snapshot and the end record carry. A reopened run (`limitsFrom` set) keeps it through every later end, so retention counts from the first end, and no install's sweep can go by a deadline the owner later extended without publishing it. `retryStep` answers `run_expired` past `runRetainedUntil` (`retention.ts`; a run settled before the field counts from `updatedAt` with the current retention). The sweep removes a run of this install past `ownRunSweptAt`, the later of that time and `updatedAt` plus the current retention, and a run another install settled last (a snapshot owner that is not this install, or a record of a run with no local copy) only `OTHER_INSTALL_GRACE_MS` past the `retainedUntil` it published: the settled snapshot's when there is one, the record's otherwise. A settled snapshot with none (settled under `never`, or by an older teamai) keeps the run, whatever the record says. Nothing is published when a run reopens: a retry its owner started before `retainedUntil` that still runs past the grace can lose its branches to another install, which the grace makes rare. A snapshot that runs, or that another install claimed after it settled (`ownedAt` later than `updatedAt`), keeps the run (`publishedRun`), and its delivered pull request branches stay too. Snapshots and records are read from `origin/teamai-reports` as the sweep's own refresh fetched it, never from the reports checkout, which keeps a dirty file through a fetch. A sweep whose refresh did not fetch `teamai-reports` just now (`RefreshResult` `unfetched`, `busy` or `failed`; a branch origin answers it does not have counts as fetched) leaves published runs and records alone, with one warning. A local run whose revision moved since the sweep read it is skipped. From that last check through the deletions and the retention marker, the sweep holds the run's cleanup lock. A kept ref or worktree that stays leaves no retention marker, so the next sweep tries again. `settledBranches` is what a settled run keeps, which the dashboard shows. `leftovers` is local, so the snapshot drops it.
- **A run changes machines only through `handoff.ts`.** `publishRun` and the claim behind `claimRun` and `resumeRun` are the only writers of `workflows/runs/<run>/state.json` on `teamai-reports`, and they write it inside `updateReports`. A publish writes only while origin shows this install (`installOwner`, from `<dataHome>/workflows/owner.json`) and the state revision this machine last saw (`acknowledged`). A publish writes `repository`, the business checkout's `getRepoIdentity`, and, for a running run with a known repository, `offered` (`handoffOf`), keeping origin's offer time; `--next` takes runs by repository, so it could not take an offer without one. An unchanged body, offer and repository write nothing. A publish checks the business origin without a lock, then answers `state_moved` when, under the locks, the run's base, a copy's commit, or the sessions it archived differ from what it checked (`checkedOutsideLocks`). Anything else that moved meanwhile is published as the locks find it, so a run a driver is still advancing can be published. `resumeRun` continues a run locally when origin has no snapshot and this machine never saw one acknowledged (`stateRevision` 0), since no other install can have claimed it. A claim reads origin under the reports lock and releases it, decides outside the lock (`definitionsOf` can fetch and sync a shared clone, and `checkOrigin` runs `ls-remote`, only for a running run: a settled one leases nothing until a retry reopens it, and the local driver's `reconcileTakenCopies` waits for that too), then writes only while origin still holds the `write` id it read (`replaceSnapshot`). The compare key is the `write` id, not the revision, because two claims of one revision both write `stateRevision + 1`. A moved or missing snapshot answers `state_moved`; a write whose push failed answers it only once a fresh read shows another write. Every claim writes the snapshot without `offered`, so a runner never takes a run another install drives, and `claimOffered` (`take: 'offered'`, behind `resume --next`) answers `state_moved` once origin no longer offers the run. When the owner's own resume or claim finds its run offered, `acquire` takes the offer away in the same guarded write (`withdrawOffer`), at the same state revision, so a runner's claim prepared against the offer answers `state_moved`. `PublishedRuns` in `src/workflow-published-runs.ts` is the one reader of the snapshots for the `resume` listing, `--next`, and the dashboard; it lives outside `src/workflow/` because it judges each offered run by the skill driver's preflight rules, which it reaches through `skill-driver.ts`, and, for the local driver, by the tool `launchToolFor` picks for each prompt step left, the one a step would run on. What the steps left need of a machine comes from `describeWorkflow`'s `facts.runs`, and `isLeft` drops the steps settled for good. For either driver, `Offer.needs` is what needs a person now: `personSteps` in `engine.ts` settles a copy of the run a claim would install (`handedRun`) and names the waiting gates the taker's `autoApprove` does not answer and the ready interactive steps. `mayNeed` names the interactive steps left and the gates left that only a person answers for that taker. Whether only a person answers a gate is `onlyPersonAnswers` in `types.ts`, the one rule the engine and the offer share. The skill driver's taker answers every gate but these, so its `autoApprove` is set: an unattended skill session that reaches a person step offers the run back (D30) as the local driver does. A `next` without `claim` calls `claimedAway`, which reads the snapshot on the reports checkout's tracking ref as of its last fetch, so it adds no network call, and answers `not_owner` once that shows another install. Every `next` that answers `done`, and every run control, calls `publishRunEnd`, which runs `publishRun` when the run was published and has ended, so origin never hands out a run its owner finished. A publish drains the run's records first, so none lands after its end. The drain (`publishPendingRecords`) drops the records of a run whose snapshot on origin names another install, so an install that ends its copy of a run it lost never replaces the owner's record. Once the end is on origin, a repeat writes nothing, so an end that a process saved but stopped before publishing reaches origin on the next request. A claim changes steps only through `takeOver` in `step-state.ts`: it releases a lease, and repends a lease in a `new` step so its next pass gets a new branch. `handoff.ts` never imports the engine. The engine calls `claimRun` for the `claim` field of `next`, and `workflow publish --sessions` passes the engine's `resumableSessions` in. What the snapshot carries is a rule table per type in `snapshot.ts` (`publish`, `drop`, or `rewrite`), so a new run or step field does not compile until it has a rule, and `parseSnapshot` refuses a field it would drop.
- **The end reached first wins.** A reported step's `settledAt` is the revision its report made. Every terminal transition, including a skip or cancellation, carries `settledAt`. A step the engine settles takes the run's current revision, which is that of the report that caused it, because every earlier revision was reconciled before that report was accepted. An open lease it fails takes the revision it was leased at, and a cancellation the winning end's revision unless it keeps an already completed agent settlement. `reportAttempt` accepts a report only after `reconcileRun` has applied every end reached before it, so an end a later report reaches never competes with an earlier one. Every end `settleScope` has yet to apply was reached at the run's current revision, and it applies the one declared first. The winner therefore does not depend on when `next` runs between reports.
- **A break is a nameless succeeded end.** A succeeded step whose `break` holds competes with the steps that reached an end by the same rule. It ends its workflow, or that workflow's loop, as success. Its value cannot change after its step succeeds, because pull rejects `break` inside a step loop's range, where a previous-pass read could change.
- **A workflow loop is decided when a round has nothing left.** Once every step of a looping workflow has settled and no end or break was reached, `decideRound` in `loop.ts` evaluates the workflow's `loop.while`. When it is false, the workflow ends with the round's outcome and outputs. Otherwise every step of the workflow repends for the next round, unless the workflow has run `max_iterations` rounds: then it fails `loop_exhausted` (`WorkflowResult.failure`, and `run.failure`, shown in `done`, at the top). A failed step alone does not stop the loop. The round is kept on the step that runs the workflow (`Scope.runner`), so `repend` resets it with that step, or on the run at the top. Pull rejects a step loop in a looping workflow.
- **A step waits for every step it reads.** `readsOf` collects the steps that the step's expressions (`stepExpressions`), templates, and `with` read. For a step that runs an inline workflow, it also collects the outer steps that the inline steps read. `skipUnreachable` uses that set to decide readiness. If a new field reads steps, add it to `stepExpressions` or `templatedTexts`. Otherwise the step can read a value before it exists, or an inline workflow can wait forever. A step outside a loop that needs or reads a step inside it also waits until the loop owner is settled (`waitsFor` in `loop.ts`), and is neither skipped nor ready before.
- **A read of a later step in the same loop is a previous-pass read, and never waits.** `previous` in `loop.ts` classifies it: the target is in the reader's loop range and needs the reader, directly or not. For an inline step, the reader is the step that runs its workflow. Pull allows the read, the engine leaves it out of the reads a step waits for, and `expressionSteps` gives the reader the target's latest archived pass (`previousPass`), which holds no pass fields on pass 1. Classify a new kind of read through `previous` too, or pull and the engine disagree on it.
- **A step loop is decided once per run of its owner.** After checking for an end, `settleScope` calls `decideStepLoop` for each succeeded owner without `loopFinal`. A false `while` sets `loopFinal`. Otherwise the range runs again through `repend`, unless a `while` owner has run `max_iterations` times, which fails it `loop_exhausted`. A loop without `while` is bounded where the owner's action would start, after the skip rule and `if`, for a leaf and a workflow step alike (`exhaustedAtStart`). The owner counts its runs in `iteration`. Pull rejects ranges that share a step and loops that wait for each other (`loopProblems`), so the engine does not check them again.
- **A pass id is never reused.** `repend` moves a step's current pass into its `passes` and bumps `pass`. `archiveUnder` moves what a repended workflow or `for_each` step ran into `run.archive`, each pass stamped `within` with the step path and pass that archived it, and `firstPass` starts a new instance after every archived pass of its path. The full record of a run is `run.steps`, with each step's `passes`, plus `run.archive`; a run record, scorer, or budget reads both. `steps.<id>.passes` is a step's `passes` plus its current pass once it settled (`passesOf`). The expression projection keeps `results` for a `for_each` pass, including in `previousPass`. Pull checks the same outputs-or-results shape in step reads and workflow output aliases.
- **An expression reads its absolute paths, wherever they are.** `expressionPaths` returns every `inputs` and `steps` path, including those inside function arguments and predicates, and never a relative path such as `.size`, which reads the current element of a predicate. `readsOf`, `skipUnreachable` and the pull read checks use it, so a new kind of expression must return its paths there.
- **Expression types are checked in two places, through `typeProblems`.** `parseExpression` rejects what an expression shows by itself, such as `x < 'a'` or `any(...) < 1`. `readDiagnostics` checks paths against the types the workflow declares. It checks each path only in the workflow that owns it, so a predicate an inline step runs over an enclosing step is reported once.
- **Pull and the engine share one list of templated fields, one list of step expressions, and one list of actions.** The templated fields are in `templatedTexts` and the expressions, such as `if` and `break`, in `stepExpressions`, both in `template.ts`. HITL declarations normalize in `parse-hitl.ts`. The actions are in `STEP_ACTIONS` in `types.ts`. Add a new field or action there, not to a copy in `parse.ts` or `engine.ts`. Pull, the cache's `prompt_file` check, the lease render and `readsOf` all split a template with `parseTemplate`, which decides which `{{ … }}` is a template, and the render evaluates it with `evaluateExpression`, as for an `if`. `parseReads` in `engine.ts` and the step parse in `parse.ts` key a table by each expression, so a new one does not compile until both say how to read it.
- **A new step status must fit five switches and two predicates.** `stopped()`, `settled()`, `takeOver()` and `stopWhere()` are in `step-state.ts`, and `retryInstance()` in `run-controls.ts`. `stopped()` decides which dependents are skipped, which steps can recover, and the run outcome. `settled()` decides readiness. `takeOver()` decides what a claim does to each step, `stopWhere()` what an end or a break does to each step under it, and `retryInstance()` what a retry does to each step in its cone. The predicates `inProgress()` and `cancellable()` in `step-state.ts` decide whether `settleScope` waits on a step and whether `cancelRun` may stop it. Each of the seven switches over every status with a `never` default, so a status added to `StepStateSchema` does not compile until all of them place it. `StepStateSchema` and the snapshot's `StepCheckpointSchema` are built from one variant list, `SHARED_VARIANTS`, so the status also reaches a handed-over run; they differ only in the `leased` variant.
- **Only the transitions in `step-state.ts` write step fields.** `waitForAnswer`, `answerHitl`, `resetPending`, `resetIteration`, `skip`, `lease`, `release`, `start`, `succeed`, `fail`, `cancel`, `repend`, `nextRound`, `endLoop` and `exhaust` change a step in place and drop the fields its new status does not have. `readRun` parses every step through `StepStateSchema`, which gives a run file from an older teamai its defaults: `settledAt` 0, `outcome` from `status`, and no fields its status does not have.
- **`run.steps` is replaced, never changed in place.** Its type is `readonly`, so `addItems`, `insertChildren` and `archiveUnder` add or remove instances by assigning a new array. An instance's `id` is `readonly` too, so an instance cannot move to another scope's group. `statesIn` in `scope.ts` keeps the instances of every scope per array, in a `WeakMap`, so settling a scope reads its own instances without scanning every step. A new array starts a new index, except that `insertChildren`, which adds the instances of a workflow a step starts, carries the old index over.
- **A pull check that changes what a file means carries a `code`.** `dropsKeptVersion` in `cache.ts` removes the cached copy when a diagnostic has a `code`. An older definition then cannot keep running with the new meaning. A diagnostic without a `code` keeps the last valid version, but only after `checkReferences` checks that version again against what the workflows it runs settle to in the same sync.
- **The workflow cache holds only what one sync settled.** `checkReferences` checks each file's version against the versions the other files settle to, and `dropUnsettled` removes every other cache entry. `startRun` relies on this: it reads the workflows a run uses from the cache and does not check them against each other again. A new way for a file to keep or lose its version goes through `checkReferences`.
- **`src/workflow/` never imports `src/benchmark/`.** The engine and its drivers know only generic primitives: clone places, `workflow: { from }`, `deliver: publish`, `finally`, `on_limit: end_turn`, `requires.strict`, `sampling: all`, `continue_on_failure`, `private`, `$TEAMAI_RUN_DIR`, `startedBy`, `run.id` and a `model` template. A benchmark is the default workflow `teamai-benchmark`, whose steps run the `teamai benchmark` verbs as commands. The `teamai/workflow-boundaries` lint rule fails any import from `src/workflow/` into `src/benchmark/`.
- **`continue_on_failure` changes only what a scope's outcome counts.** `settleScope` in `engine.ts` fails a scope for a stopped step unless the step's definition has the key; the step's own status, and the rules for its dependents, stay as they are. `keptResults` in `fan-out.ts` gives such a `for_each` step the results of its settled items when it stops unsettled, on a timeout (`expire` in `limits.ts`) and on a cancel (`cancelRun` in `run-controls.ts`).
- **A fallback reads why a step failed, never only that it failed.** `currentStep` in `scope.ts` gives a settled step's `failure` (code and message, current pass only) to expressions and templates; `stepFieldSchema` in `expression.ts` types it, and `undeclaredField` in `parse-context.ts` refuses a field it lacks. A migrated default that kept a success-shaped fallback guards it on the code, and ends the run `failed` on a code the fallback must not hide, such as `tool_unconfigured` for a tool the member names that cannot run: `continue_on_failure` alone would let the run succeed with nothing done. A command that exits `INPUT_REJECTED_EXIT` (65) fails `input_rejected`, and one that exits any other non-zero status fails `command_failed` (`commandEnd` in `protocol.ts`), so a failed command step's `failure` is never null. `explainFailedSteps` in `workflow-commands.ts` offers no retry for `input_rejected`, and says `command_failed` by its message alone, which names the status. Under a shortcut, whose progress already showed a command's stderr, it names a failed command step by its exit status only, so each message is said once.

- **Retry validates every container before resetting any.** `retryContainers` in `run-controls.ts` climbs from the target through scopes and fan-out items until a running runner or the top. Each dependency cone includes needs, reads and loop waits, or item after dependencies. An independent standing end or break rejects the retry. When the run ended, its `$TEAMAI_RUN_DIR` is gone, so each cone also takes, transitively, the `needs` of a `workspace: { confined }` step in it (`confinedWriters`) and the steps whose outputs, `results` or `passes` a step in it reads in a template (`templatedTexts`, never only in `if`) as an absolute path inside that directory (`runDirProducers`: compared by normalized path, since the removed directory has no real path). `retried.runsAgain` lists every step besides the target that runs again, and `workflow retry` prints it. The apply pass archives replaced passes and descendants, reopens settled runners with `start` to keep inputs and round, then bumps revision and reconciles. Only the targeted loop owner's iteration resets; the top-level round does not. An answered refused approve or succeeded choose is retryable too, so a changed answer resets its dependent branches. A HITL request in the cone that is waiting, or answered and not yet run, starts a new pass too, so its answer is asked again in the new context and an answer to the old pass is stale. Unanswered skips in every affected container reset so skips caused by cancellation can run again. Retry's prelude reconciles without finishing a provisional outcome. Reopening refuses a run past its `retainedUntil` (`run_expired`), then clears the run's end, failure, `retainedUntil` and endRecordQueued flag, and removes its queued end file through records.ts. These three pieces stay consistent: run state, the pending end record, and published stats. The next end upserts the same record path; stats replace the origin end's outcome and duration contribution with the new end's, without adding another run. Replaying the same endedAt contributes nothing.
- **The local driver keeps tools and questions interruptible.** A single question joins command and prompt exits in the driver's race. An interactive tool owns the terminal alone: no question opens while it runs, and starting one aborts and closes an open question. A poll closes the question when its own step is leased or a different step or pass waits; an unrelated lease leaves it open. It polls next every second while asking, every two seconds while tools run, and aborts a replaced HITL request or cancelled prompt. `src/tool-launch/process-stop.ts` shares process stopping between commands and adapters. Headless tools detach and stop with SIGTERM; interactive tools stay attached and stop with their captured descendant tree. Foreground interactive signals reuse env-exec's terminal detection and signal policy: when the terminal reaches the child, teamai ignores SIGINT and SIGQUIT, while SIGTERM and SIGHUP are forwarded and stop the driver. Interactive adapters inherit stdio and accept an optional result file. Repository edits are kept for interactive steps; only headless prompts run the read-only check. A nonzero interactive exit without a result reports its exit status. `leaseNext` records the identity of the latest driver that called next in `RunState.driver`, without capabilities. Resume uses this machine's open local lease workspace, then run.driver.workspace for a local driver on this machine, then cwd. Controls pass run.driver to finishRun so end records retain the driver kind.

- **One local driver owns a run on this machine.** `takeRunLock` in `store.ts` takes `driverLockPath` with `acquireLock`, waiting at most the caller's `waitMs`, and releases it in finally; the `RunLock` it passes is the proof a caller holds it. It answers `held` with the body's value or `busy`, so no answer of a body reads as a busy lock; `withRunLock` turns `busy` into the `driver_running` error for a body that answers an envelope. `withDriverLock` in `local-driver.ts` takes it without waiting. `runLocalDriver` drives inside it, and `workflow resume` also claims inside it, so a claim never lands under a driver already running the run. A live holder returns `driver_running`, including its pid, before anything is claimed or driven; the existing lock machinery reclaims dead owners. The driver lock spans tool execution and questions, while `withRun` holds a different run lock only during one engine operation. Neither lock's scope is extended by the other. Every HITL decision without a HITL driver logs once when the engine changes the step. HITL replies carry one literal `respond` command template, which drivers display unchanged.
- **Judge work is a step of a `teamai-score` run, and no scorer holds a run open.** Which passes are judged comes from facts already on disk: the run files, each run's scorers at its team pin (`RunScorers.of`), the `installId` that `reportAttempt` stamps on each pass it settles, and the marks and labels under `<dataHome>/scores/`. Scoring never writes a run file, so a run's counts, tokens and failure cannot move. A run settles without waiting for a judge. A step whose scorers set `sampling: all` has every pass judged, whatever its scorers sample: a benchmark trial's prompt sets it with `start: workflow`, the benchmark's own `score` step judges each trial, and its `report` step reads their labels from that step's results in the run file. The evidence of a step that runs in a clone is staged into `scores/evidence/subjects/` before the clone can go, and that is all its judges read, so no teamai-score run of such a step starts before its evidence exists: a prompt's by `stagePassEvidence` in `place/place.ts`, which `settleManaged` calls once the place is finished and before the engine accepts the report, and which removes it again when the engine does not accept a success; a workflow step's by `stageSettledEvidence` in `place/clone.ts`, which `withRun` in `engine.ts` calls for each step the operation settled `success` before it saves the run, as such a step settles in a later `next`, once its last step does, so neither its teamai-score run nor a dependent starts before its evidence. `sweepClones` removes a clone once its run is not running or no step in it is still to settle, with the evidence staged for each pass there that did not succeed, since a report killed before the engine answered leaves evidence no judge reads. A staged copy goes once every mark of its pass is closed: `score write` or `score settle` removes it when it closes the last one, and `score subjects --lapsed` when the marks expired; a mark open or waiting for CI keeps it. Every scored pass of a step without `scorers.start: workflow` gets a run of its own, for every driver: the answer that settles it, `managedReport` for a report and `inProcessClient.next` for a `workflow` step, which settles on `next`, calls `startedByPasses` (`src/scorers/engine-hooks.ts`, the one door from `src/workflow/` into `src/scorers/`). It runs `PassScoring.start` (`src/scorers/pass-scoring.ts`), which starts one root `teamai-score` run per settled pass of a scored step this install judges, `startedBy: cli`, recorded for the scored run's driver and from its checkout, and the answer lists each run that scores a pass of it and has not ended in `data.started` (`{run, step, pass, scorers}`), every answer again until that run ends, so a driver that crashed finds them on its next call. A refused start is logged and never fails the answer. The driver drives each listed run as its own: the local driver hands them to its `started` option, and `withPassScoring` in `workflow-commands.ts` drives them before the command returns, attended or not; the skill driver ticks them as child runs (J7 to J10); an external driver runs `workflow next` and `report` on them. An exclusive start key per pass, `<dataHome>/scores/started/<run>/<hash>`, keeps a retried settle or a second process from starting it twice. A run that ended more than the 14 days a mark lasts ago starts nothing, and each start removes the keys of such runs and of runs that are gone. Pull warns on a `scorers.start: workflow` step that no `workflow: teamai-score` step after it reads `teamai score subjects --step` for (`ScoreSubjects.unreadWarnings`).
- **A delivered pass can be labelled before its judge.** For a pass of a `deliver: pr` step, the `check`, `ci` and `protected` steps of its `teamai-score` group run `teamai score stage` (`src/scorers/score-stage.ts`) on the evidence before the judge step: the scorer's `check` (`checkStage` in `src/scorers/scoring-stages.ts`, through `runCheckAt` in `src/scorers/check-run.ts`, on the delivered head with the `protect` paths restored from the work's starting commit), the delivered commit's CI (`deliveredCi` in `pr-delivery.ts`, through the provider's optional `PullRequestLookup.checks`), then a `protected_path` failure. The first that fails decides the group: the judge step is skipped, and `label` (`src/scorers/score-labels.ts`) gives the scorer's highest label below `passingScore`, with `decidedBy` set to that stage. A check that cannot run fails the group as `check_could_not_run` and writes no label. `score plan` groups a scorer with a check alone, never batched. The run page's judge count leaves stage-decided labels out.

## Session driver workspace preparation

`workflow next --prepare` prepares through `place.ts`, as the local driver does; it never implements graph semantics. A lease whose place another open attempt holds (`placeHeldBy`) answers `busy` and stays leased, as the local and skill drivers queue it. An attempt the run stopped holds its place too, for the driver that held it, until that driver reports it and the report abandons the place, since what it started may still run there (`otherLeases` lists that driver's `run.stoppedAttempts`). Another driver's stopped attempt holds nothing, as that driver may be gone and never report it. `--attempt <a>` prepares an attempt the driver already leased: `prepareAttempt` in `protocol.ts` lists every other lease of the run as running, with `canTakeLease: false`, so the engine hands that one back, and answers `wrong_attempt` when it does not, naming the release when the re-hand gave the attempt up because the driver's `can` no longer covers the step. `--adopt <dir>` makes a writer's copy a place the host made (`place/adopted.ts`). `adoptRefusal` checks it and changes nothing: an attempt already prepared elsewhere and a step in the checkout adopt none, and a reader only the place the host made for its branch, and the place must be the top of a worktree sharing the checkout's git directory, clean, on the branch or detached at its start while no such branch exists, with the start in its history and every lease commit present after `fetchMissingCommits`. A place that fails answers `adopt_mismatch`, and the attempt stays leased; so does a place another open attempt began to adopt (`placeHeldBy`), with the message `prepareHostPlace` refuses it with. `takeAdopted` then points its hooks at the empty hooks directory and switches a detached place onto the branch. Setup runs there on the first prepare, unless an earlier attempt of the run finished in that place. The skill driver prepares a writer on `h3` through `prepareHostPlace`: `host` goes on in the place the last attempt on the branch finished in while it passes the checks, else answers `needs-place`; `adopt` answers `needs-place` with `refused` for a place that fails them, or that another open attempt began to adopt (`placeHeldBy`). Every other lease on a branch whose last attempt finished in a place the host made (`adoptedPlaceOf`) goes on there while it passes the checks, a command's and a reader's included, and TeamAI makes the copy once it does not; `placeHeldBy` counts that place too. Every prepare in `protocol.ts` takes its lease, checkout and the run's other leases from `leasedPlace`, and its busy rule from `placeLeased`. The record keeps `adopted` whatever the lease's role, so `releasePlace` leaves the place, and a failed setup puts the branch agent files back instead of removing the worktree. The `core.hooksPath` `takeAdopted` set is unset again at every end of the attempt there: a prepare or setup that failed, a finish of any outcome, and an abandon. Setup marks the place it runs in until it finishes (`markSetup`), and `adoptedMismatch` refuses a place that still has the mark: what a setup that failed or was cut short left there would pass the next setup's checks, so the host makes the place again. Attempt-local metadata contains paths, workspace contracts and fingerprints only. Repeated next calls reuse that metadata without reapplying an overlay over agent edits. Public report reconciles cancellations before git, checks driver/revision ownership, finishes through the shared local workspace helpers, and cleans up only after the engine accepts success with cleanup. Git network operations run under the run lock too, such as the push that finishes a writer, and the fetch of the run's branches (`fetchMissingCommits`) by a prepare that opens or adopts a copy lacking a commit the lease needs. A skill driver's foreground call waits `TICK_LOCK_WAIT_MS` for the lock, then answers `driver_running`. The existing per-run driver lock serializes local and public preparation/report. Run lookup scans configured local data homes by id and rejects duplicates, independent of cwd; the run's checkout governs git work.

A skill child's `result.json` may carry `changed`, paths relative to the place. A missing field means none. The skill driver passes that list into finish in process, not on the public report. `finishPlace` uses it only for an adopted writer: a path git would commit that the child did not list, a rename's old path included, fails `unreported_changes`, and nothing is committed or pushed. A path the preparation merge staged, whose content still matches that merge, is not unreported. A failure from a step that ran is replaced by `unreported_changes` when a path is missing. A failure that stopped the step before it ran, such as `model_unavailable`, is kept, and the file is still not committed. When the list covers every such path, only those paths are staged, so a file written after the check is not in the commit. A place TeamAI made, and a report that does not pass the list, still commit the whole tree, which is what `--adopt` from another driver and `adopt-host-place` do. A command in an adopted place that is already dirty does not start. A path that still matches the base agent overlay prepare recorded is not that dirt, so the command starts, and finish puts the branch's copies back when the command left them unchanged. A file that command writes while it runs is still committed. An ignored path is not part of the check.

## The skill driver

`drivers/skill/` runs a workflow from a coding session. The agent runs only the literal commands each reply prints. A detached runner per attempt, `workflow report <run> --driver skill --attempt <a>` with `TEAMAI_WORKFLOW_ATTEMPT=<run>/<a>` (`attempt-marker.ts`), prepares the attempt's place under the run lock and runs its setup outside it; then it runs a command step outside the lock and reports it, or writes a prompt step's brief and offers it to the agent, which hands it to a child agent; the child reports it, from whatever coding session it runs in. A runner holds the attempt's `runner.lock` while it lives, which is how a tick tells it is alive. Setup and a command each run in a process group of its own, recorded in the attempt's own `group-<pid>.json` as it starts (`recordGroup` in `tool-launch/process-stop.ts`), so neither displaces the other; a runner killed while either runs leaves that group running, so C10 and C11 stop every group the attempt recorded (`stopRecordedGroup`) before the step runs again or its place is given up. Windows has no process groups, and there a setup or command a killed runner left runs on. `skill-state.ts` is the only writer of `runs/<run>/skill.json`. `journal.ts` appends `runs/<run>/journal.jsonl` beside it, after each call's answer: a line for each call a session makes on the run (the call, who made it and whether from the run's checkout, the attempt or step it names, and its answer code), and an `asked` line for each dispatch and person action the first time a turn shows it. It holds no env value, input or session id, no turn prints it, and the driver never reads it but to journal an action once. An error thrown inside an agent's call answers `skill_call_failed` with its message and `next: null` (`runSkillCall`), so the agent always reads one envelope; a runner's own call lets it go on up, as nobody reads its answer. `transitions.ts` holds the rows below as `TRANSITIONS`, and one row function per input, such as `replyRow` or `pollRow`, returns the row it took with only what its caller needs: the new state and its effects, or the error the call answers. `tick.ts` and `skill-runner.ts` save that state and apply the effects through one interpreter, `applyEffects`. `workflow-skill-transitions.test.ts` compares these tables with `TRANSITIONS` cell by cell, both ways, and walks every row through `runSkillCall`, so a row lands in both places or in neither.

**Run states**, derived from skill.json and never stored as a field: `none` (no skill.json for this run, or no run yet), `host` (the run has prompt steps and the agent has not answered the host question), `drive`, and `done` (the engine answered `done`). **Attempt phases**: `preparing` (its runner prepares its place), `queued` (another open attempt of the run holds its place), `placing` (it waits for the agent to adopt a place its host made), `running` (its runner runs the command), `offered` (its dispatch is shown, not acked), `dispatched` (acked: a child works it), `stopping` (the engine cancelled it, or its `expiresAt` passed: its runner stops its command, or the agent stops its child and reports it), and `reporting` (a write-ahead report body is stored).

**Order of one call.** Parse options with zod; for a resume or a takeover, R22, before the lock, whose file would leave `runs/<run>/` behind a refusal on a machine that lacks the run; take the run lock (D19); S rows; the row of the input; a tick; build the turn; save; release; journal the call. A start `WorkflowClient.start` refuses after R10 answers its error with `next` the describe literal only for a refusal another answer fixes (`ANSWERABLE_START_REFUSALS` in `skill-driver.ts`: `invalid_inputs`, `confirm_needed`), and null for the rest. **A tick** sends the reports a crash left stored (P11), gives up attempts stopping by a runner that is gone (C11), respawns the runners of queued attempts whose place is free (D9) and of attempts whose lock is free (C10), then calls the engine `next` (D1), takes D2 to D5 for each attempt its `cancelled` lists, then H5, and applies its reply, repeating while a lease comes back and a slot is free, once more when a reply to a call's `next` with no slot gave up an attempt that waited (D2), so the slot it freed is leased in the same call, and once more after the last lease while a gate is journalled, so that reply, made with no slot, says whether the gate still waits; then, for a call, it ticks each run `scoring` lists (J8), in `drive` and in `done`. **A poll** (`--wait`) repeats lock, tick, release and a `WAIT_POLL_MS` sleep until one of D22 to D25 applies. Runners take C rows under the same lock and never take S rows. **An agent's report** (`report --attempt` without the marker) skips the session check when the agent reports the attempt (S6), since a child an app's orchestration tools start has a session of its own; it takes its P row, sends the report and saves under the lock, then answers as a runner does, with no tick and no turn, so it leaves the session's events for the orchestrator's next call. **A runner's check**: while its command runs, a runner ticks every `RUNNER_POLL_MS`, and once at the attempt's `expiresAt`, with `canTakeLease` false. The engine applies deadlines only when it is called, so the check at `expiresAt` is what turns an expired attempt into a stop (D3, C9).

### Judges

A pass the scoring module started a `teamai-score` run for is judged by that run, which the skill driver drives as a child run while judging is on or the session judges (J7 to J10). Each child keeps its own skill.json, with `scores` naming the parent, and the parent's call ticks it: its command steps go to the background runner, and its confined judge step is the same dispatch or background run a step of the parent would be. The parent's `judging`, `judged` and `judging-off` events and its `done` `judging` report it, and its `done` waits for it with `then: poll`. The child's skill.json keeps the run's declared `done` outputs as the engine gave them; only `scoredLabels`, through `src/scorers/engine-hooks.ts`, reads labels from them, and outputs it cannot read end the judging with `run_unreadable` (J10). With `--no-judge` the run is still started, and stays running for `teamai workflow resume <run>`.

When describe's judging is by the session (`Judging` `session`: no verified judge of the session's tool here, and a scorer that accepts `best-effort`), skill.json keeps `sessionJudge` instead of `judging`. The skill driver then offers the confined judge at `best-effort`, `read` access, on the tool of the session that drives the run now, which a takeover changes, so each judge step of its `teamai-score` runs comes to the session as a confined dispatch, as `skill-data/workflow/references/judging.md` says. On `h4`, which starts no child agent, R13 turns `sessionJudge` into `judging` at `best-effort` when the session's tool runs confined here, so the background runner judges instead, and drops it otherwise. A start or resume with `--no-judge` keeps neither.
