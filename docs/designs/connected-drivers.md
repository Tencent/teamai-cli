# Connected drivers

> Status: Proposal — workflow drivers become named, overridable definitions whose runtimes run steps in sandboxes (containers, native sandboxes, hosted sandboxes), T3 Code threads, other teamai installs of a fleet or anything else, nested where one needs another, while teamai keeps the git, credential and evidence boundary and knows nothing about the technology a runtime uses.

Tracking: workflow-first (#1589), Paseo adapter (#1087, maintainer-owned), runtime integration (#818).

## Problem

teamai has two in-process drivers, `local` and `skill`. `workflow start` and `workflow resume` refuse any other `--driver` (`src/workflow-commands.ts` before this design). A process can already drive a run over the CLI protocol ([your own driver](../guide/workflow-advanced.md#claim-from-your-own-driver)), but it re-implements the loop, git rules, recovery and session capture, and nothing in teamai runs a step in a container: the local driver claims `sandbox` from a config flag (`src/types.ts:882`).

Workflow-first (#1589) makes drivers teamai's only execution system. Teams need drivers they can add, share and override as they do workflows, and steps that run in sandboxes, T3 threads or remote machines with the same workflow file.

## Principle

teamai owns the boundary; runtimes own how a process starts somewhere.

| teamai owns | A runtime owns |
|---|---|
| Preparing and finishing the place: overlays, role delivery, commits without delivered resources, hook-safe git (`untrustedGit`, `src/workflow/worktree.ts:119`), push, protected paths | Starting a process in a container, a VM, a T3 thread or elsewhere |
| Which env each process gets, what is withheld (`SANDBOX_WITHHELD_ENV`), secret masking | Mapping the place view onto its technology (mount flags, user mapping, copy in and out) |
| Evidence: tool transcripts on the host, judging through the `teamai-score` runs teamai drives, `deliver: publish` of sessions and labels | Its own options, images, pools and endpoints |
| Recovery: kept work on failure, `retry`, `resume`, publish and claim | Reporting the isolation it really enforces |

teamai core imports no sandbox, T3 or Paseo code. The core holds the primitives below, the `host`, `tools` and `fleet` runtimes, and a toy runtime for development and tests; the first-party runtimes are separate packages that speak the protocol.

## Terms

- **Driver definition**: a named YAML resource, selected by `--driver <name>`. It lists runtimes and their options.
- **Runtime**: where and how a step executes, not which tool runs in it. `host`, `tools` and `fleet` are built in and run in process (`use: local` is the old name of `tools`); every other runtime is an external process. A runtime reports the capabilities it really enforces.
- **Host slot**: `host`, in every definition and never listed: commands, setup and `answer:` steps in teamai's process, on the worktree as it is. **`tools`** launches the member's tools for prompt steps and judges, in the member's own home.
- **Place**: unchanged, the worktree or checkout an attempt works in (`src/workflow/place/`).
- **Place view**: what teamai gives a runtime to work on a place: paths with their access, the attempt's tool home, and credentials.
- **Handle**: the runtime's id for one opened place, which teamai persists in the attempt directory to reconnect after a restart.
- **Fleet**: the teamai installs that take attempts a run offers through `origin`; each is a **member**, and the run's install stays its **owner**.
- **Composition**: a runtime that runs `through` another, which opens the place first and passes its handle on.
- **Operation**: one `open`, `exec` or `prompt` call, named by an id teamai writes to the attempt directory before sending it.
- Not to be confused with a "local route" in describe (`docs/dev/workflow-engine.md`), the part of a definition only the local driver can run, or with `Executor` (`command` | `prompt`, `src/workflow/requirements.ts:322`), or with the "agent runtime" of other products, which means the tool, or with the bundled runtime (`src/bundled-runtime.ts`), the Node and shell that WorkBuddy and CodeBuddy ship, which teamai uses to run hook commands.

## Runtime protocol

JSON lines over stdio, `protocol: 1`, validated with zod on both sides: `@teamai/runtime-protocol` (`packages/runtime-protocol`) holds the request and reply schemas teamai and every first-party runtime parse with, the one runtime package `src/` imports. An operation is accepted first and finishes later, so a runtime can run work that outlives one request.

| Primitive | Request | Reply and events |
|---|---|---|
| `init` | options | the options validated by the runtime (a bad key fails before any step); its offer as a `can` (`CanSchema` in `@teamai/runtime-protocol`, which exports its type as `Can`), including `tools` it can run, and `exec: false` when it runs no command, so command steps and setup go to the next runtime (D3); `prompt: true` when it launches agents its own way; `confinedPrompt: true` when it answers a prompt confined to a directory, without which teamai drops `confined` from its offer. The request also carries `credentials`, the names of the env credentials and the logins the definition gives it, never a value, so a runtime offers only what it can sign in |
| `open` | operation id, run and attempt ids, place view (none for a confined prompt's place), credentials for this attempt; for a composed runtime, the outer's handle | `accepted` with a handle; then `ready`, or `failed`. A second `open` for the same run and attempt returns the same handle |
| `exec` | operation id, handle, argv, env, unset, credentials (a prompt's tool gets the ones its runtime declares, a command step none; sent again with a resent operation, so a restarted runtime needs to keep none), cwd | `accepted`; `output` events tagged `stdout` or `stderr`; then `exited` with the exit code and the stdout, up to 64 KiB and past that its end after a marker (teamai keeps the whole stdout it streamed), or `cancelled` |
| `prompt` | operation id, handle, lease (step, tool, model, the whole prompt with its result instruction, the result file, session to resume, permissions, interactive, turn cap), env, `provided` (the names in env the team provides, apart from the step's own env and the attempt's markers, so a runtime that keeps env in plain text can drop them), unset, credentials (a judge gets only the ones a confined run of its tool reads here: its profile's and the common proxy and CA variables), cwd; for a step confined to a directory, `confined` (`dir`, the `level` and `access` the step needs, the output `schema`) | for a runtime whose `init` said `prompt: true` (T3, Paseo): `accepted`, before any slow launch; `display` once the agent exists, with its link, which neither accepts nor ends the prompt; then `finished` with the tool's session, `resumed: true` only when it continued the session the lease asked to resume (without it teamai records a fresh session), the result JSON the agent wrote and usage, and, for a confined prompt, `confined` with the level and access it enforced, never above it; or `failed`, or `cancelled` after a `cancel`. teamai writes the result to the attempt's result file and keeps the step's timeout with `cancel` |
| `collect` | handle | the working tree written back into the place, deletions included, never committed, with the result directory and the attempt's tool home; after success and after failure |
| `cancel` | operation id | No separate answer; the operation ends `cancelled` once no process of it still writes the place, or `failed` with `cancel_failed` when its stop cannot be confirmed. teamai waits at most 15 s for an exec or prompt's cancel outcome, live or during recovery; without a confirmed stop it keeps the place, records and login |
| `reattach` | handle | `gone`, or `alive` with each operation's state, including a terminal outcome teamai has not yet recorded: an exec's exit and stdout, a prompt's `finished` session, result, usage and `resumed` |
| `close` | handle | `closed`; the runtime may drop the handle's retained outcomes. Or `close_failed` with a failure: the place, and what runs in it, may remain, so teamai records it on the attempt, shows it in run details, and keeps the attempt's login held. A runtime that exits while an exec or prompt runs fails it `runtime_lost`, and keeps its login the same way |

Every request gets an answer. A `reattach`, `collect` or `close` the runtime cannot answer, such as when its journal cannot be read or its provider cannot be reached, gets the failure reply for its handle (`{"event":"failed","handle":…,"failure":…}`), never `gone`; an operation it cannot carry out ends `failed`. A cancel the runtime cannot confirm ends the operation `failed`, with `cancel_failed` and the cleanup step, and `reattach` keeps reporting it: teamai then neither collects nor closes the place, keeps the login, prints the runtime's message, and the next `teamai workflow cancel` of the run tries the stop again; from the moment the runtime reads that cancel, `reattach` reports the operation `running` until the new stop is confirmed or fails again. `teamai workflow cancel` opens each runtime in `recover` mode, which runs no sign-in or tool check, gets no credentials, offers nothing and answers from its journal; only a runtime that refuses that mode is opened for new work instead. An `{"event":"error"}` names no request, so teamai fails every request still waiting on that process with `runtime_unanswered` (an `exec` or `prompt` in flight ends `lost`), and an `init`, `reattach` or `close` with no reply within 15 s, or an `open`, `exec` or `prompt` with no answer within 15 s, the same way; a `cancel` has no answer of its own, and an `exec` or `prompt` teamai waits on that has no outcome within 15 s of its cancel ends `lost` the same way. The attempt keeps its place, records and login. `collect` and the end of an accepted `exec` or `prompt` have no bound yet: that needs a deadline on `open`.

Recovery rests on two rules. teamai persists the operation id before it sends a request, and a runtime returns the same acceptance and the same terminal outcome for a repeated id until `close`. So a teamai that dies between a runtime's reply and its own write loses nothing: it repeats the request or `reattach`es and reads the outcome. A finished `exec`'s retained outcome carries its stdout up to protocol 1's 64 KiB bound, and past that its end, so teamai rebuilds the session, usage and stop reason it would have read live unless the command printed more than that. An `exec` still running when teamai restarts is cancelled and its attempt reported failed with its work kept, because the budget teamai meters from live output cannot be enforced across the gap; a `prompt` reconnects.

A prompt on a runtime that launches agents, not through another, keeps its place open while a step not yet settled continues its session in the same workspace, inside one `workflow` step that opens it (`heldFor` in the attempt runtime record, outside `max_parallel`); a top-level step gets a place of its own, so none is held for it. The later step's prompt names that conversation (`continue: {handle, op}`) and is one more turn of it; the runtime finds it by the conversation's id, and the close of the later place ends only that place's own turns. The held place closes once no step continues it, at the run's end, on a handoff, and on `workflow cancel` or `--release`. A through entry never holds one: it would keep the step's credentials past the step.

`exec` gets the lease's scoped env, never teamai's `process.env`. teamai still does everything its own launch does around one (`runStepLaunch`, `@teamai/tool-launch/run-step-launch`): it builds the argv with the family's step profile, reads the result file, parses stdout for session, tokens and cost, enforces `limits.budget` from `output` events and stops a step with `cancel`, and turns a driver abort into the same `cancel`. `cancel` stops the whole process group, as `stopProcess` does. A probe the adapter runs before a launch, such as OpenCode's major version, runs through the same `exec`.

A runtime that keeps the place on the host (a bind mount) returns from `collect` without copying. A runtime that copies the place (a hosted sandbox) writes it back in `collect`: when `collect` returns, the host worktree, deletions included, the result directory and the collecting attempt's own tool home hold what the place holds, and only then does teamai finish the place. Copy-back stays inside the place: it resolves every parent with `lstat`, never writes or deletes through a symlink, writes a link as a link, and rejects an entry whose path leaves the place.

## Place view

- The prepared worktree read-write, mounted or copied **at the same absolute path** as on the host, so tool transcripts keep the host `cwd`.
- Every git path read-only: the common git directory, which holds the worktree's admin directory (with `config.worktree`, `worktree.ts:453`), and the `.git` pointer. A path inside another one is given only through it: mounted at its own path, Docker Desktop keeps it from being removed while the container runs and makes it again when the container starts after it went. The step edits files; teamai stages and commits on the host with `untrustedGit`, so no hook, fsmonitor, replacement, filter, diff or merge driver, signing, ssh, askpass, editor, pager or pack program the step planted in the copy's config runs there. A runtime mounts or copies them read-only as they are. A strict sandbox withholds the forge variables, but it does not scrub git config: a checkout that keeps forge auth there (`actions/checkout`'s persisted `http.<url>.extraheader`, `checkoutCredentials` in `src/utils/git.ts:468`) stays readable by the step, so a team that needs the step kept from it checks out with `persist-credentials: false`.
- The **workflow folder** read-only, when the step's workflow is a folder: the copy teamai pinned under the data home, at the path `$TEAMAI_WORKFLOW_DIR` names, so the step reads the files the folder carries where it runs (`placeView` in `src/workflow/steps/runtime-steps.ts`, and a fleet member's `runtimeCommand`). A step's own `env:` cannot widen the view: `WorkflowFolder.named` accepts only a path teamai pinned.
- The attempt's **result directory** read-write at its host path: the result file moves to `attempts/<attempt>/out/result.json` (`src/workflow/store.ts:94`), because the attempt directory itself holds `place.json` and the saved overlay. teamai reads it after the step, as today.
- A **tool home per attempt and tool** under the attempt directory, read-write, set through the variable the tool's session store reads (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `CODEBUDDY_CONFIG_DIR`; `SESSION_PLATFORM_FACTS`, `src/session-flow/adapters/platform-facts.ts:6`). Each attempt owns its home, so parallel attempts never share one and `collect` mirrors only the collecting attempt's home; a retry or a later pass seeds its new home with the resume state of the recorded predecessor home, so `--resume` finds the session. Session lookups for the run's steps (resume in `local-driver.ts:406`, skill use, step scoring, `teamai-score` evidence, session publishing) read the store inside the home the attempt's record names: `sessionStoreDir` (`src/locate.ts:1490`) takes that tool home in place of the member's, so it still adds the store's own directory (`projects` for Claude), and `AgentSession` hands the result to the adapter, which already takes a store directory (`packages/tool-core/src/formats/claude-code.ts:463`), because recorded tool roots are paths under the member's home (`recordedToolRootDir`, `src/types.ts:3798`) and cannot name an attempt directory. The report keeps the transcript's `filePath` (`agent-session.ts:34`), so publishing reads exactly that file. A tool whose store has no such variable is not in the runtime's `tools`: OpenCode, because its adapter reads sessions through the `opencode` CLI with the host's env and uses the store directory only to check it exists (`packages/tool-opencode/src/session-adapter.ts:457`), and its login lives under `XDG_DATA_HOME` too; Pi, because its launch adapter has no step profile (`packages/tool-pi/src/launch.ts`). The member's own tool home is never exposed. The built-in `tools` runtime keeps the member's home, as today.
- The run's **scratch directory** (`runDir`, the step's `$TEAMAI_RUN_DIR`, a name `@teamai/runtime-protocol` exports as `RUN_DIR_ENV` and a runtime package never spells, `teamai/launch-env`) read-write at its host path, so steps of one run hand files to each other through it as on `local`. Every run path is spelled by its real path (`runsDir`, `src/workflow/store.ts`), so a process resumed under another spelling of `HOME` names the same files as the one that started the run. Integrity rests on the hash checks `teamai-score` keeps on what it reads there.
- A confined prompt gets none of the above: only its `dir`, read-only, never the run's scratch directory. teamai spells `dir` as the run spells its scratch directory and the prompt names it only as `confined.dir` exactly as sent, so a runtime may mount or copy it at a neutral path and replace that text in the prompt, keeping the member's home, name and project out of the judge's view.
- Files the step writes are owned by the host user; how is the runtime's concern.
- Credentials travel with each `exec`, never set when the sandbox is created, so setup gets only setup's keys (the `can.setup` contract) and each `exec` unsets the withheld names with `env -u`, keeping the sandbox's own env (its `PATH`, and the placeholders `sbx` agents read for proxy-managed logins).
- Setup runs through the runtime's `exec` with setup's keys only; teamai keeps its dirty and secret checks, ignored files included, on the result (`src/workflow/place/setup.ts`). A runtime that copies the place collects after setup, so those checks run before the prompt. A runtime that cannot run setup reports `setup: false`.

## Decisions

| # | Decision |
|---|---|
| D1 | Pull. A runtime never sees the run's graph; it gets places, commands, prompts and cancellations. A runtime that runs whole workflows (`can.workflow`, the fleet) also gets a `workflow:` step whose steps it can run on its own: a member sees only the sub-graph it was offered, which it reads from its own team definitions. |
| D2 | The parent loop is the local driver's loop, and it reaches every runtime through one `Runtime` interface with the primitives above. In process: `host` (commands, setup and answers on the worktree as it is), `tools` (`@teamai/runtime-tools`: the member's tools in the member's home, launched through `@teamai/tool-launch` on the host process adapter), and `fleet` (D16); every other runtime is an external process on the protocol, behind a stdio client of the same interface. The launch library (`@teamai/tool-launch`: argv, result file, stdout, budget) is shared by all of them. The raw CLI protocol stays for drivers with a loop of their own. |
| D3 | Capabilities belong to a runtime. Each `next` offers one runtime's `can`, provisionally, under one driver identity, listing every open attempt in `running` (`engine.ts:1813`, `:1834`). Today the loop sends `alone: true`, which fails a step on a `tools` or `unattended` hold (`engine.ts:2001-2014`); that judgement changes to take the definition's runtime offers as a list of complete `can`s, never merged field by field: a step fails only when no single runtime's offer can take it, and start's strict-sandbox refusal applies the same rule to every definition (`workflow-commands.ts:518`). A `wait` is final only after every runtime with room was offered, in definition order (`local-driver.ts:1228`). Before an `open`, teamai records the attempt's runtime; after `accepted`, its handle. After a restart it reconnects one attempt at a time: `reattach` its handle, offer its runtime's `can` and list every other open attempt in `running`, so the engine hands back exactly that attempt (`engine.ts:1929-1930`) instead of releasing it (`:2077-2079`). A `gone` handle is collected if possible, then closed, and the attempt reported failed so `retry` applies. A step confined to a directory that no runtime offers waits; once only such steps are left, the loop stops with `confined_pending`. |
| D4 | Definitions resolve in this order: the member's own (`~/.teamai/drivers/<name>.yaml`), then workflow scope precedence (`resolveStart`, `src/workflow/cache.ts:169`): the project's team definition, then the user scope's, then teamai's default. teamai never writes into `~/.teamai/{drivers,runtimes,tools}/`, so team code cached under the data home never reads as personal. A personal definition may replace a team one: the workflow's `requires` and `strict` still hold at admission, so it cannot drop a sandbox a step demands. A run that `resume --next` took for another member, and every fleet member, ignore personal definitions, so a handed-over run does not depend on the machine. Within the team, two namespaces defining one name is `driver_namespace_conflict`. A shipped driver's canonical name is its stored name: `t3` and `teamai-t3` both resolve as `teamai-t3`, options key included. `local`, `none`, `skill` and `fleet` are reserved: a definition is named only what `parseDriver` (`src/workflow/driver-name.ts`) reads as a driver outside teamai, so a name teamai reserves later is refused there too. `--driver local`, the default driver, ephemeral runs and shortcuts run the definition `teamai-local` (`runtimes: [use: tools]`, no tool), resolved as any other: the member's, then the team's, then teamai's; a run that takes the member's or the team's says once which file it took, so a team override of every member's default driver is never silent. |
| D5 | Personal and workspace tuning goes through `workflows.drivers.<name>` in user and workspace config, merged by key as `workflows.tools` and `workflows.allow` are (`src/config.ts:554-556`); the runtime's options schema validates the result at `init`. |
| D6 | An external runtime is a resource like a driver definition: `runtimes/<name>.yaml`, whose `entry: { command }` names an executable on PATH, or a folder `runtimes/<name>/` whose `RUNTIME.yaml` names its code with `entry: ./<file>`; both declare `protocol` and optionally `exec`. The resolver (`src/resources/resolver.ts`, row `runtimes`) reads it from the member's own `~/.teamai/runtimes/`, then the team root and its active namespaces (two namespaces with one name is `runtime_namespace_conflict`), then teamai's package, whose `runtimes/teamai-<name>.yaml` names its own `bin` with `entry: { bin }`; each name is looked up exactly in every layer first, then as `teamai-<name>`. Nothing is found on PATH alone. A runtime the lookup selects that cannot run (its marker does not parse, its `protocol` is not `RUNTIME_PROTOCOL`, its entry is missing, or it is reached through a link) fails the run naming its file; another layer never stands in for it. A personal runtime is the member's own code and needs no acceptance. Before the first spawn of a team runtime, a person accepts a folder at its revision, or a file's command at the file's content as a tool instance's is; an attended run asks, an unattended one refuses. A member's or team's runtime that replaces teamai's says so once per run, and each attempt's record names every runtime's layer, location and revision. What the `sandbox` runtime builds is a resource of its own, a sandbox profile: `sandboxes/<name>.yaml`, or a folder whose `SANDBOX.yaml` sits beside the files it builds from (a `warm.containerfile` is then `./<file>` of the folder, and the warm key holds the folder's revision). An entry names it with `sandbox: <name>`, `default` when unset (teamai's `teamai-default`, sbx); the lookup is the runtimes' own, and teamai reads the file and hands its options and `profile: { name, revision, folder }` to the runtime at `init`, so the runtime's schema stays the one check of the options. Provider options on the entry fail naming the profile to move them to; `credentials` and `max_parallel` stay on the entry, which is the driver's. The record names the profile, its layer, location, revision, provider, and what `init` said it enforces (`isolation`, `network`, `tokens`, `max_turns`). |
| D7 | Every lease picks a runtime from its requirements; a step never falls back to the host to satisfy isolation or env; a `requires.network: false` the runtime cannot enforce is listed in `unenforced`, or waits when strict (`requirements.ts:465`, `:437`). A runtime offers only the workspace modes it supports (omitted means read-only, `workspace.ts:770`). Every definition has a **host command slot**: the implicit `host` entry, which needs no agent (teamai, git and the shell) and launches no prompt step's tool; it takes the place of the definition's `tools` entry in the order, else comes last. A step it runs is recorded `host`, and a prompt on `tools` is recorded `tools`. The slot takes command and setup steps when no runtime of the definition execs them, and otherwise only what stays on the host: the command steps of every workflow teamai ships (pinned by workflow name, `DefaultWorkflows.isShipped` in `offerTerms`, `engine.ts`), every `deliver: publish` step, and every `answer:` step, which the member's tool answers on this host (the `host` entry answers it through the tools runtime's answer launch; a start judges its strict requirements on this host's slot); external runtimes refuse both (`host`). The pin is a partial outcome: it covers every shipped default, but a team copy of one under another name escapes it. A step requirement only the host slot offers would close it, so a step says it needs the host instead of its workflow's name deciding it. A step confined to a directory runs on a runtime whose `init` declares confined prompts, or, when the definition lists `tools`, on the host's tools; the `host` entry offers none. Routing never reads `private`, which says only that a run's sessions and outputs stay on this machine. |
| D8 | Push and PR delivery stay as today: teamai pushes and opens PRs; a runtime that opened one reports `changes.pr_url` (`engine.ts:2777`). A strict sandbox withholds the forge variables from every process teamai starts (`requirements.ts:81`); what the sandbox technology itself exposes is a known limit (First-party runtimes). Outside one, a step may receive credentials the team declares, but the run's branch is always pushed by teamai, because its commit keeps delivered resources out and its checks guard protected paths. |
| D9 | A runtime declares `env` only for processes whose env it controls. Credentials travel in `open`, per attempt, never inside a command string, and never `SANDBOX_WITHHELD_ENV`; each `exec` gets its scoped ones (Place view). A `NAME: env:<VAR>` credential is read from the member's environment once at start, failing `credential_missing` when `<VAR>` is unset, kept in memory only, and masked in what teamai keeps; only a runtime that offers `can.env` takes one, and `local` none (both `bad_option` at start). A tool login kept in a file is a `login` credential, and the member's daily login is never copied: Codex rejects a refresh token used twice (`refresh_token_reused`, `codex-rs/login/src/auth/manager.rs` in openai/codex), so a copy that refreshes logs out every other holder. `codex: login` reads a dedicated Codex home, `~/.teamai/logins/codex`, which the first attended Codex step that needs it creates for the member with `CODEX_HOME=~/.teamai/logins/codex codex login`, after one line saying why; an unattended one fails `credential_missing` naming that command. That login has one live attempt at a time, across runs and runtimes on the member's machine, held by a teamai lock per login, not Codex's `auth.lock`, which guards only the file write while the token refresh happens before it (`codex-rs/login/src/auth/manager.rs` and `storage.rs` in openai/codex). The lock belongs to the attempt, not to a teamai process: it is taken before `open` copies the file, recorded with the attempt, and kept across a driver restart until the attempt's final operation has stopped and its final collection and login write-back have completed, or the attempt is closed; a collection after setup does not release it. It is never reclaimed because the process that took it died. A `gone` attempt whose home cannot be collected releases it and reports `login_not_written_back`. A run waiting on the lock names the run that holds it, and `teamai workflow cancel` of that run releases it. At `open`, teamai copies the dedicated `auth.json` into the attempt's tool home; after `collect`, under that lock, it writes it back to the dedicated home by compare-and-replace, keeping its permissions, and only when it is a regular file that parses as a Codex auth file for the same account; otherwise it keeps the old one and reports `login_not_written_back` with the fix (`CODEX_HOME=~/.teamai/logins/codex codex login`). Parallel Codex steps on that login therefore run one after another; parallel Codex steps need `sbx`'s own login or `OPENAI_API_KEY`. A provider with its own credential broker (`sbx secret set openai --oauth`) needs no copy. A keychain-only login does not cross into a runtime; the step fails naming the variable it needs (Claude: `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`). |
| D10 | No new unattended flag. A runtime earns `isolation: sandbox`, `env: true` and `unattended: true` by enforcing them; the existing admission rule (`admission.ts:208`), strict hold (`requirements.ts:448`) and `negotiate` (`requirements.ts:410`) do the rest. |
| D11 | Drivers name an execution integration (`local`, `skill`, `t3`, `sandbox`, `paseo`, later `orca`). Any definition may set the default `tool`; the shipped presets (`claude`, `codex`, `opencode`) are definitions over `local` that only do that, and a team's `sandboxed` may set `tool: codex` over `sandbox`. A step that names another tool still runs on it. A tool `local` launches runs on a runtime that execs when the place has its executable and its session store can live in the attempt's tool home: Claude, Codex and CodeBuddy, with their variants. |
| D12 | Recovery keeps today's rules: a failed attempt keeps its work (`collect` runs after failure too), `retry` opens a new pass, which starts from the base like any pass and can read the failed pass's kept work on its branch, `resume` reattaches, publish and claim move the run. After `collect`, `finishWriter` runs unchanged (`src/workflow/place/writer.ts`): it restores the overlay, then commits, so delivered resources stay out. Its git calls (`commitWork`, `offBranch`, `pushIfOrigin`, `worktree.ts:921`, `:382`, `:953`) run with `untrustedGit` for every runtime. A `private` run keeps its sessions and outputs on this machine, so it has no publish or claim recovery. |
| D13 | Testing: the toy runtime and a scenario suite exercise every primitive (accepted and finished, cancel, collect after failure, reattach after a killed driver, options schema) through the `Runtime` interface; `local`, `fleet` with two installs, the toy runtime over stdio and each first-party runtime run the same suite, so `--driver local` keeps its behavior under it; the conformance harness gains their capability profiles (`conformance-interpreter.ts:101`); each slice adds one real-CLI run. |

## First-party runtimes

Each is a private workspace package (`packages/runtime-sandbox`, `packages/runtime-t3`, `packages/runtime-paseo`) that `src/` never imports, shipped as its own executable (`teamai-runtime-<name>`) inside the `teamai-cli` package, built as its own tsup entry beside today's `src/bin.ts` and `src/index.ts` (`tsup.config.ts:51`) so its `bin` entry names a file the package holds, and reached only through the stdio seam, as anyone else's runtime is. The workspace is the one the tool packages design introduces.

**`teamai-runtime-sandbox`**: one runtime, one `provider`, which the entry's sandbox profile names (D6), two families that differ only in how the place view reaches the sandbox. Each provider declares only what it enforces, and none falls back to the host: a provider that is not available fails `init` with how to fix it.

No runtime declares `can.network`, as the skill driver does not (`docs/guide/workflow.md`): `requires.network: false` is listed in `unenforced`, and a strict one waits (`requirements.ts:465`, `:437`). Each provider declares the isolation of its technology, with nothing to check at `init` beyond that the provider is available.

| Provider | Family | What it is | Declares |
|---|---|---|---|
| `sbx` (Docker Sandboxes), the recommended one | bind mount | a microVM with its own kernel and Docker daemon, made with `sbx create <template> <worktree> <path>:ro …` from the template of the attempt's tool (`claude`, `codex`), the `agent` option's when set (a tool or a kit reference), or the bare `shell` template for a command step's place, and named `teamai-<home id>-<run>-<attempt>`, removed with `sbx rm --force`; the workspace and extra paths at their host paths through virtiofs; `sbx exec` returns the command's exit status; outbound TCP goes through a host proxy under the member's `sbx policy`; service logins (Claude: `sbx run claude <dir>`, then `/login`; Codex: `sbx secret set openai --oauth`; an API key: `sbx secret set anthropic`) stay on the host and the proxy injects them | `isolation: sandbox`, `env`, `unattended`, `setup` |

| `bwrap` (Linux), `seatbelt` (macOS 14 or later) | bind mount | no image: the host's toolchain on PATH, read-only; a private home; never root | `bwrap`: `isolation: sandbox`, `env`, `unattended`, `setup` without root. `seatbelt`: `isolation: worktree` and no `unattended`, because it has no PID namespace, so a strict `isolation: sandbox` step never runs on it |

- **Bind mount.** The place view is mounted at its host paths with the access the view gives each path; `collect` copies nothing.
- **Copy.** `open` recreates the place view at the same absolute paths inside the sandbox (worktree, git paths and the workflow folder read-only, result directory, the attempt's tool home); `collect` copies them back as the protocol requires; a setup step is collected before the prompt (Place view). The provider's own auth (`VERCEL_TOKEN` with `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID`, or `VERCEL_OIDC_TOKEN`) is the runtime option `provider_auth`, read on the host and never forwarded into the sandbox. Every sandbox teamai creates on Vercel, the warm image's scratch sandbox included, is `persistent: false`, and an attempt closes with `delete()`, never `stop()`, so a stop or a timeout leaves no snapshot of an attempt; every copy-family adapter must turn such a persistence default off. The provider's SDK is bundled into the runtime's own executable, so teamai's own start-up does not load it. Other hosted providers (E2B, Modal, Sprites and the like) come later, each in its own issue when users ask for it, and are open to contributions: each is one provider adapter over the same copy contract.
- **Warm image.** When `warm` is configured, providers with an image start attempts from a cached warm image: the toolchain and the package manager's store already filled, never a file of the checkout or a secret. `warm` names a recipe on a base: a `containerfile` (`docker`, `podman` only; its build context holds only the `cache` files), or a `prepare` command run once in a scratch sandbox on the base (`image` for `docker`/`podman`, the configured `agent` or kit for `sbx`, the `runtime` for `vercel`) with no attempt workspace and no step or setup credential. `cache` lists the dependency manifests and lockfiles `prepare` needs (`[package.json, package-lock.json]`); `docker`, `podman` and `sbx` bind-mount them read-only into the scratch sandbox, so nothing of the checkout is copied, and `vercel` copies them in and deletes them, with the scratch project's `node_modules`, after `prepare` and before the snapshot. A `containerfile` that copies the `cache` files puts them in the image by the team's own recipe. The key is a hash of the base, the recipe and the `cache` files. The warm image is made at the first `open` for its key, because the key needs the place's `cache` files, which `init` does not have; concurrent `open`s for that key wait on one build, and a failed build or `prepare` fails that `open` with its last lines. It is reused while the key is unchanged. `docker`/`podman` build or `commit` it as an image tagged by the key; `sbx` runs `prepare` in `sbx create <agent or kit>`, then `sbx stop`, `sbx template save <sandbox> teamai-warm:<key>` and `sbx rm`, and creates attempts with `sbx create -t teamai-warm:<key> <agent>` (`--pull never` is the default for a saved template); `vercel` snapshots only the scratch sandbox with `sandbox.snapshot({ expiration })` (an omitted `expiration` means 30 days from last use) and creates attempts from `source: { type: 'snapshot' }`, preparing again when the snapshot expired or is missing. `bwrap` and `seatbelt` use the host's toolchain, so `warm` is `bad_option` there. Setup still runs in each attempt's worktree with teamai's checks; the warm image only makes it fast, because the worktree is mounted or copied over the image's working directory.
- **Logins.** A tool is offered only where it can sign in: with `sbx`, the login sbx keeps for its service (`sbx secret`); else a sign-in variable teamai gives each exec by name, the definition's `credentials` or, when it declares none, the tool's own variables found in the member's environment; else, for Codex, the dedicated `login` (D9), which teamai does not copy when the runtime reports `ownLogins`; for a tool there, it sends none of the variables it found in the member's environment either. `sbx --cloud` has no host workspace and copies; it waits with the other hosted providers.
- **Known limits.** A strict sandbox keeps the withheld variables out of every `exec`; it is not a network or host firewall. Docker Desktop's `host.docker.internal` and an Open `sbx` policy reach services on the host, `sbx` forwards the host's SSH agent by default, whose socket stays usable by path even though each `exec` unsets `SSH_AUTH_SOCK`, and its proxy injects a stored global forge secret (`sbx secret set github`) into every sandbox's requests to that forge; a member who needs that separation turns forwarding off in `sbx`, scopes or removes that secret, and keeps a closed policy.

## Definitions

Each part a run uses is a resource the resolver reads with layers: a driver definition, a step runtime and a tool instance, each a file `<folder>/<name>.yaml` or a folder `<folder>/<name>/` holding `DRIVER.yaml`, `RUNTIME.yaml` or `TOOL.yaml`, of the member, the team root or an active namespace, or teamai.

```yaml
# drivers/teamai-t3.yaml, shipped; --driver t3
schemaVersion: v1alpha1
name: teamai-t3
description: Run each prompt step as a T3 Code thread in a worktree teamai prepares.
runtimes:
  - use: t3
    options: { environment: local, max_parallel: 4 }
  - use: tools            # prompts T3 cannot take; commands run on the host slot
```

```yaml
# drivers/sandboxed.yaml, a team's own
schemaVersion: v1alpha1
name: sandboxed
description: Run every prompt in a Docker Sandboxes microVM, on members' subscriptions.
runtimes:
  - use: sandbox                                               # profile default: teamai's teamai-default, sbx, each attempt from its own tool's template
    # Each member signs in once: Claude with `sbx run claude <dir>`, then /login; Codex with `sbx secret set openai --oauth`
    options: { max_parallel: 4 }
  - use: tools
```

```yaml
# sandboxes/hosted.yaml, a team's own: the same, in a hosted sandbox
provider: vercel
provider_auth:                                                 # read on the host, never forwarded
  VERCEL_TOKEN: env:VERCEL_TOKEN
  VERCEL_TEAM_ID: env:VERCEL_TEAM_ID
  VERCEL_PROJECT_ID: env:VERCEL_PROJECT_ID
```

```yaml
# drivers/hosted.yaml, a team's own
schemaVersion: v1alpha1
name: hosted
runtimes:
  - use: sandbox
    sandbox: hosted
    options:
      credentials: { CLAUDE_CODE_OAUTH_TOKEN: env:CLAUDE_CODE_OAUTH_TOKEN }
  - use: tools
```

```yaml
# ~/.teamai/config.yaml, a member's own tuning
workflows:
  max_parallel: 8
  drivers:
    sandboxed: { runtimes: { sandbox: { max_parallel: 2 } } }
```

A runtime's `max_parallel` caps its own open attempts under the run-wide `workflows.max_parallel`, which stays the outer cap: the engine applies it when set (`engine.ts:1941`), and the local loop takes 1 when it is not (`local-driver.ts:1118`).

Another hosted sandbox or a cloud VM is one more provider of `sandbox`'s copy family, or its own external runtime on the same protocol: create in `open`, `exec`, copy in `open` and out in `collect`, destroy in `close`.

## Composition

The case that needs it: a step visible in the T3 app that runs fully isolated.

```yaml
# drivers/t3-sandboxed.yaml, a team's own
runtimes:
  - use: t3
    through: sandbox
    sandbox: sbx                                 # a provider at isolation sandbox: sbx, or docker with node in the image
    options:
      t3: { instance: claude-t3-sandbox }        # a T3 provider instance whose Binary path is teamai's wrapper
  - use: tools
```

`sandbox` opens the attempt's sandbox on the place view at the same absolute paths and owns its lifecycle. `t3` launches the child with `modelSelection.instanceId` set to a T3 provider instance (T3 Settings → Providers, for example "Claude (t3-sandbox)") whose Binary path is a wrapper teamai ships inside `teamai-runtime-sandbox` (its `tool-exec` mode). The wrapper knows no tool: it is one multicall executable that takes the tool from the name it was called by (`teamai-sandbox-<tool>`), resolves that tool's `command` from the tool registry, finds the sandbox open for its working directory by the attempt's label (`teamai-<run>-<attempt>`), and runs that command there with its argv, stdio, exit status and signals passed through. teamai ships one `bin` per shipped tool, generated from the registry; a team or personal instance is a symlink named after it. A tool it serves must be in the sandbox runtime's `tools`, be installed in the sandbox, and be one T3 drives over stdio; a T3 provider reached on a local port cannot cross the sandbox. With no attempt for its working directory, or a tool it cannot resolve, it exits non-zero and never runs a session on the host. Parallel children share the instance: each runs in its own attempt's worktree, so each wrapper lands in its own sandbox. The child lives in the member's own T3 while the tool runs in the sandbox, and teamai finishes the place on the host as for any runtime. Paths must match, and the tool must not reach this machine's ports, so only a bind-mount provider at `isolation: sandbox` serves as the outer. The wrapper gets the prompt's scoped env from the sandbox runtime over a per-attempt unix socket (mode 0600, in a 0700 directory under the attempt directory), never from T3's env and never on disk, including the tool-home variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `CODEBUDDY_CONFIG_DIR`) aimed at the attempt's bind-mounted tool home, so the transcript lands where resume, scoring and `score --drain` read it. `t3` launches the child idle and sends the prompt (`t3_thread_send`) only after the wrapper connects on that socket; a wrapper that never connects fails the attempt with `isolation_unproven` and nothing is sent, so an instance whose Binary path is not the wrapper runs no prompt on the host. The `instance` option names the instance; `init` fails, naming the setup step, when it is missing. teamai knows the isolation is real because the wrapper is its own.

A definition may also compose by delegation, with no `through`: a fleet member drives each lease with its own `--driver`, so a pool of members may run every step in sandboxes on their own machines.

## Fleet

Runs as a whole already move between machines: a run published while running is offered on `teamai-reports`, and `teamai workflow resume --next` on another install claims it, skipping what that machine lacks (`docs/guide/workflow-advanced.md`, "Offer a run to a runner"). The fleet does the same for single attempts, so one run spreads its steps over VMs, other machines, remote containers and linked T3 environments, each with teamai installed, using only git.

```yaml
# drivers/fleet.yaml, a team's own
runtimes:
  - use: fleet
    options:
      pool: build                          # members that take this pool's attempts
      stale_after: 30m
      can: { isolation: sandbox, env: true, unattended: true, workspace: [new, continue] }
      max_parallel: 10
  - use: tools
```

A member is any install that runs `teamai workflow resume --next --pool build --driver <its definition>` in a checkout of the business repository.

| Phase | Owner (the `fleet` runtime) | Member |
|---|---|---|
| `open` | Prepares its place without the lease's merges (the member does them, so the owner never holds an open conflict), records `rangeFrom`, pushes the start commit to the attempt's ref `teamai/attempts/<run>/<attempt>` with a ref push, and writes the offer: the lease rendered for one attempt (step, tool, model, prompt, rendered `env`, workspace, merges, setup, role, limits, requirements), its team commit and the pool. It never writes an argv, a credential value or a local path. | `--next` takes the oldest offer of its pool and repository it can run, skipping what it lacks with the reasons `--next` gives for runs, by replacing the record with its claim; a member that lost the race gets `state_moved` and tries the next. |
| run | Waits on the record; `reattach` reads it, so a restarted owner loses nothing. | Takes the run lock for the run id with no run file, keeps the attempt directory in its own data directory, prepares its place from the attempt's ref, does the merges, and runs the lease through its own runtimes with the per-lease code the local loop uses (prepare, launch, `finishWriter`), never `managedReport`. It writes progress to the record while it runs. `finishWriter` commits failed work too; the member pushes it to the attempt's ref. |
| `finished` | A prompt lease ends as `prompt` does: the member's normalized result (outcome, result JSON, failure, session tool and id, usage, limit), and the session's archive entry. A command lease ends as the local loop reports one (`commandEnd`, `src/workflow/protocol.ts:964`): exit code, JSON outputs from stdout, and a stderr snippet in the failure message; the complete stdout stays on the member. | Archives the session with `archiveSessions` (`src/session-flow/archive.ts:153`), which scrubs secrets and rewrites local paths; `score --drain` would archive nothing, because it walks only local runs and the member has no run file. Then it writes the result, the commit range and the archive entry into the record. A record `publish`'s checks refuse is written as a failure naming the field, so the owner fails the attempt at once instead of waiting. |
| `collect` | Fetches the attempt's ref, restores its own overlay (`restoreOverlay`), and fast-forwards the place to the record's `changes.to`, never to whatever the ref holds later. `finishWriter` then records `rangeFrom..to` and pushes the workflow's branch to that tip. Scoring runs on the owner, which has the run: `collectEvidence` reads the member's archive entry by the member's session id, never a restored copy, because a restore writes a new session id (`deriveTargetSessionId`); without the tool's session adapter there, the evidence records `transcript_not_found`, never a wrong score. | — |
| `cancel` | Writes a cancel into the record: an offer nobody claimed is `withdrawn`, a claim becomes `cancelling`. A claim nobody answers expires past `stale_after`. | Reads the record between progress writes, at least every 30 seconds, stops the step as a driver abort does, pushes its work, and records `cancelled`; the owner takes that work as for a finished attempt. |

A member restarted after a crash finds its claims among the records on `teamai-reports`, stops the process groups its killed run recorded, and finishes each claim from the work its attempt's ref holds, or answers its cancel. A member that stays gone stops writing progress; once the last progress write is older than the pool's `stale_after`, the owner reports the attempt failed and `retry` offers a new pass on a new ref, which starts from the base and can read the work the record's last pushed commit kept. A late push or record from the expired member changes nothing: its ref is not the new pass's, and the owner accepts only the claim it holds. `fleet`'s `can` is a promise the definition makes, so `--next` takes an attempt only on a member whose own driver offers every key of it, and a member that cannot keep a strict step fails it as the local loop would. The fleet needs a git team repo with `teamai-reports` and a business repository with `origin`, as runners do.

A `workflow:` step goes to the fleet as one attempt when a member can run its sub-graph on its own: a workflow file, or an inline workflow whose steps read nothing around it but the inputs, whose steps are command, prompt or gate steps working in the step's copy, with no copy of their own, team role, delivery, answer step, nested workflow or person at the tool, on a step with no `on_limit: end_turn` (`wholeFit`, `src/workflow/whole-workflow.ts`, the one rule the owner and the member judge by). The engine leaves such a step unstarted at reconcile while the run's driver has a runtime that takes it whole (`run.takesWhole`), and starts it there otherwise. `next` leases it whole to a runtime with `can.workflow`, judged as one reduction over its steps, and starts it for any other asker, which then gets its first step, so a run resumed without the fleet still runs. The record carries the step path and the inputs its `with` renders, or for an inline workflow the inputs its steps read, and what the budgets around the step have left (`budgetLeft` in `engine.ts`); the member checks the step still goes whole in its own copy of the workflows at the run's team commit, renders the inputs again, drives the sub-graph as a private nested run (`createRun` and its local loop on its own driver) in the attempt's clone with no origin, takes the run's copy into the clone and pushes it to the attempt's ref. The nested run's budget is the smallest of the step's, its workflow's and what the record says is left, so its steps stop where the owner would stop them; the member returns what they spent, which the owner counts against the budgets around the step, also when the owner cancelled the attempt (the `cancelled` record carries it, and the owner's driver reports it for the stopped attempt) or a restarted member ran the step again (the nested run the killed one left comes out of the new one's budget and joins what it returns). The owner settles the step from the run's outcome, end and outputs through `finishStep`, as for a workflow step whose children ran here. A gate the nested run reaches goes to the owner through the record: the member writes it as the record state `asking`, and keeps asking in its progress; the owner's wait shows it to its person, or answers it as its driver answers its own gates when nobody answers there, and writes `answered`; the member reads the answer between its progress writes, as it reads a cancel, and its next progress is `claimed` again. No person sits at a member's tool, so the fleet declares no `hitl` and no interactive step goes to it.

## Out of scope

an Orca runtime; Paseo session resume across passes; a T3 thread in another environment without teamai installed there; starting fleet members on demand (a person, a job or a T3 thread starts them); tools added without a teamai release (the tool packages design); workflow gates through T3's own approval UI (gates use `workflow respond`, and a required approval stays with the person's terminal); shell-template runtimes; an `ssh` runtime; migrating the local driver's own tool launch out of the core; in-process loading of team code; extension points other than drivers; hosted providers other than Vercel Sandbox, `sbx --cloud` included; Cua Spaces as a sandbox provider (it mounts no host folder, `sendFile` copies one way into `~/Downloads`, no download is documented, and `space.bash()` documents only stdout), though a Space with teamai installed can run a fleet member today, without a strict sandbox, because a member needs forge push credentials. Each needs its own accepted scope.

## Direction

Everything that executes a step goes through the `Runtime` interface: `local` in process, external runtimes over stdio, `fleet` to other installs. Later integrations (Orca, more sandbox providers) are runtimes or providers too, composed with `through` when one needs another's place, and new tools reach every runtime through the tool packages design. A runtime or tool that needs a change in this interface changes the interface for all of them. What a team adds to run steps (a driver definition, a step runtime, a tool instance) is a resource kind with a resolver row, never a lookup of its own, so it gets namespaces, folders and the member's own layer the same way.

## Risks to check

- Whether children launched with `delegatedFrom` show inside the parent thread and notify it when they finish, as delegated tasks do, and where the runtime gets the session's `environmentId` (an MCP lookup by thread id); T3 may ignore `delegatedFrom` on a local launch, so the runtime checks after the first launch whether the child lists the parent, and otherwise launches threads of their own. T3 slice 1 checks this first.
- Whether a child launched over MCP can use its question tool with the question shown in the T3 app, and whether "result file written after the person says it is done, and thread idle" is a reliable end for an interactive step. If either check fails, the runtime declares `hitl: false` and interactive steps stay held, as today.
- Whether a T3 thread launched idle starts its provider's binary, so the wrapper connects before the prompt; if not, slice 13 ships without `full-access` through a sandbox.
- Whether a T3 terminal carries `T3CODE_THREAD_ID` and whether it inherits an agent session variable; without the first, a `deny` run started there makes threads of their own; with the second, it cannot start there and the person uses another terminal.
