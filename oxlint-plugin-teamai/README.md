# oxlint-plugin-teamai

This repository's own lint rules. `npm run lint` loads them through `jsPlugins` in `.oxlintrc.json`, as `teamai/<rule>`.

| Rule | What it stops |
|---|---|
| `teamai/home-env` | HOME reads outside `packages/shared/src/home.ts`. |
| `teamai/learnings-root` | Manual learnings-root joins outside their owner. |
| `teamai/configured-tool-paths` | A `path.join` or `path.resolve` (also `host.path.…`) outside `src/locate.ts` that takes a tool's configured `skills`, `rules`, `claudemd`, `settings`, `agents`, `hooks`, `mcp` or `mcpProject` field: joined by hand, a path under `$HOME` misses a home that moved, such as an instance's `home.env`. Use `locate()`, `toolPathUnder()` or `hookSettingsFile()`. It sees the field where the call names it, or in a `const` read from it or destructured from its object before the call; a field passed through a parameter or a template string is not caught. |
| `teamai/launch-env` | Launch environment literals outside `src/launch-context.ts`. |
| `teamai/launch-through-workflows` | Launching an AI tool outside a workflow driver: an import of `src/tool-launch/call.ts` or `run.ts`, or of `runConfined` from `confined.ts`, from outside `src/workflow/` and `src/tool-launch/`; or a process call (`spawn`, `execFile`, `exec`, `crossSpawn`, `execa`, `execCommand`, `probeBinary`, `execute`) there whose command is a tool's executable, unless its arguments start with `--version`, `claude plugin`, `opencode serve` or `opencode session`. Run the AI work as a workflow step (`docs/designs/ai-through-workflows.md`). Tests and type-only imports are exempt. `BASELINE` lists today's callers and may only shrink; a listed file that stops launching is reported until its entry is removed. |
| `teamai/workflow-boundaries` | Workflow entry-point violations and transitive skill-to-local dependencies. |
| `teamai/no-provider-merge` | Merge operations in providers and delivery, and forbidden delivery/snapshot dependencies. |
| `teamai/windows-tests` | POSIX constructs in the current `WINDOWS_TESTS` selection. |
| `teamai/rules-locate` | MCP path lookups during rules activation. |
| `teamai/workflow-failure-codes` | Unclassified failure producers and unexplained forwarded codes. |
| `teamai/config-load-options` | Missing preview options at named `loadLocalConfig`, `loadLocalConfigForScope`, and `autoDetectInit` calls outside their owner. Forwarded options are accepted; wrapper behavior still needs tests. |
| `teamai/remove-delivered` | A call of `remove` from `fs-extra` or `src/utils/fs` in `src/pull.ts` or any file under `src/resources/`, which leaves a stale entry on the delivery record when it deletes a delivered copy (#1577). Use `removeDelivered(ledger, dest)`. A new file under `src/resources/` is checked without being listed; a delivery written elsewhere is not. |
| `teamai/attempt-result-writes` | A write to an attempt's result file outside `src/workflow/attempt-result.ts`, which would keep any credential its body repeats. Use `AttemptResult.write(file, body, secrets)`. It recognizes the file by `attemptResultPath(...)`, a name bound to one, or a `resultPath`: a path passed on under another name is not caught. |
| `teamai/family-facts` | A tool family's facts module (`src/facts.ts`, `src/definitions.ts` or `src/detect.ts` of any `tool-<name>` package, and `FACTS_FILES` in the rule) importing anything but facts modules at run time, a dependency or a dynamic import included; and a static import from a startup entry that reaches a family's behaviour, which the report names as a chain. The startup entries come from the tree: each executable `package.json` `bin` names, through `tsup.config.ts` `entry` (a step runtime's own executable excepted), the CLI bundle it loads by URL, each module the CLI's `hook-dispatch` and `pull` commands load, and each module one of those loads with `import()`. Read a family at startup only through `@teamai/tool-definitions/facts`, and load its behaviour with `import()` where it is first needed. A new family package, executable, hook step or pull step is checked with no change here; a `bin` that `tsup.config.ts` does not name stops the lint. |
| `teamai/process-reads` | A `/proc/…` path as a string or a template, or `/proc` itself as an argument (`readdir('/proc')`, `path.join('/proc', …)`) or the start of a sum, in production source under `src/` and each package's `src/`, in a module that never calls `tellProcessRead`. Linux answers from `/proc` the process reads macOS runs ps for, and the agent wait budget runs on Linux, so an untold read hides a wait macOS has. Tell it with `tellProcessRead` from `@teamai/shared/process-group`, once per ps it stands for, or read through process-group. A bare `/proc` elsewhere, as a sandbox's mount argument, reads nothing and passes; one first stored in a variable is checked where that variable is an argument, the start of a sum, or the head of a template that goes on with `/…`. |
| `teamai/tool-facts` | A list of tool ids, or a table keyed by tool that leaves some out, outside `src/tools.ts`. Put the fact in `TOOLS`, or key the table by every tool (`Record<ToolId, ...>`), so a new tool fails the type check until it is decided. An ordered registry, an alias map or a frozen history table carries an explained disable. It checks `src/` and `packages/*/src/`, against the shipped ids in `tool-ids.generated.json`, which `node scripts/check-docs.mjs --write` writes from the tool registry; a missing or empty file fails every production file instead of checking nothing. |
| `teamai/yaml-parse` | `YAML.parse` or yaml's `parse` outside `packages/shared/src/yaml.ts`. Use `parseYaml` (`@teamai/shared/yaml`), which returns JSON values instead of a Set, Buffer or Date for `!!set`, `!!binary` or `!!timestamp`. |
| `teamai/package-boundaries` | A workspace package (`packages/<name>/`) importing `src/` or any repository file outside itself, a relative import into another package instead of its name (`'../../tool-core/src/definition.js'` → `'@teamai/tool-core/definition'`), `src/` importing a `packages/runtime-*` package but `runtime-protocol` and `runtime-tools`, which runs in teamai's process (its tests may import `@teamai/runtime-testing`), a runtime package importing another runtime but `runtime-protocol`, `runtime-kit` and, from tests and `src/testing/`, `runtime-testing`, `runtime-protocol` importing more than `@teamai/shared` and the tool-core levels, home and usage, `runtime-kit` importing more than the protocol and `shared`, `tool-launch` importing a runtime package or, outside its tests, a value from a module that starts a process (`PROCESS_STARTERS`, as in `teamai/tool-family-shape`) or `@teamai/tool-definitions` (a runtime bundling it would carry every family: the caller resolves the tool, and tests and `src/testing/` may read the registry), and a package whose `package.json` is missing `"private": true`. It reads `import`, `export … from`, TypeScript's `import x = require()`, `import()`, `require()` and `vi.mock`, a template with no placeholder as a literal; an `import()` or `require()` whose module name is computed is reported in a package and in production `src/`, since its side cannot be checked: disable that line saying why the module is outside the repository. A new folder under `packages/` is checked with no change here. |
| `teamai/tool-registry` | Importing `TOOLS`, `LAUNCH_ADAPTERS` or `ADAPTER_REGISTRY` outside the registry (`src/tool-registry.ts`, and `src/tool-launch/tools.ts` for launch adapters): `import { TOOLS } from './tools.js'` then `TOOLS[tool].autoCompact` becomes `descriptorOf(tool).autoCompact` from `./tool-registry.js`. Readers not moved yet are listed in the rule's `NOT_YET_MOVED`, which only shrinks: an entry that stops reading a table fails until it is removed. Tests are exempt. |
| `teamai/shipped-tool-ids` | `isToolId` or `isAgentToolId` in production source outside the registry, beyond a file's count in `SHIPPED_ONLY`. Both are false for a tool instance, so a fact read through them skips it: resolve the name with `toolOf`, `baseDescriptorOf`, `agentFormatOf` or `toolHomeOf`. A check that must hold only for a shipped tool takes a `SHIPPED_ONLY` entry with its reason; the list only shrinks. The same goes for a comparison of a tool name with Claude Code's or Codex's id, the tools an instance extends (`tool === 'codex'`, `case CODEX_TOOL_ID:`, `CODEX_TOOL_IDS.some(...)`, a substring test `tool.includes('codex')` or a lookup `tools.includes(CLAUDE_TOOL_ID)`), beyond a file's count in `BASE_ID_COMPARISONS`, where each file says why its comparisons must be false for an instance; compare `baseToolOf(tool)` or ask `isCodexTool(tool)` instead. Not counted: a comparison of a resolver's call (`baseToolOf`, `agentFormatOf`, `hookFormatOf`, `mcpFormatOf`, `launchAdapterIdOf`, `familyOf`), of a `.base`, `.format`, `.family`, `.kind`, `.launch` or `.ecosystem` field, or of a local never reassigned from one or a parameter typed `ToolName`, `AgentToolId`, `ModelAgent`, `McpFormat`, `HookFormat` or such a field's type (`AgentTool['format']`); nor a case of a switch whose `default` assigns what it switches over to `never`, which the type check holds only for a closed union. Not caught: a tool's own name held in a field with one of those names, a comparison through a list (`['claude', 'codex'].includes(tool)`) or a `Set` or map lookup, and a name passed to another function that compares it. |
| `teamai/tool-home-env` | Setting a tool's home variable on an env outside `src/tool-launch/tools.ts`, in production source, each package's included, and `scripts/`: any string spelling one of `HOME_VARIABLES` (every variable that moves a shipped tool's home, pinned to `toolHomeVariableNames` by `src/__tests__/tool-home-env-variables.test.ts`), so a tuple loop, `Object.assign` or `Reflect.set` is caught by the literal it starts from; and an object key or a member assignment named after one, or computed from `.envVar`, `.homeEnv`, `.rootVariable`, `.env`, `homeVariableOf(...)` or `deliveredHomeVariableOf(...)`. A variable set by hand misses an instance's own variable and the home a member recorded: spread `toolCommandEnv(name, home)` instead; a package, which cannot import it, takes the variables from its caller, as a session adapter takes `SessionHost.homeEnvAt`. Reads (`env.CODEX_HOME`, `env['CODEX_HOME']`), deletes, types, test support and the test-only `packages/tool-testing/` pass, and so does a spelling in the files that name the variables as data (`NAMING_FILES`: the descriptors and launch profiles, `src/tool-registry.ts`, `src/tool-home.ts`, `src/types.ts`), where only the write forms are checked. Not caught: a name built at run time (`'CODEX' + '_HOME'`), a name another function returns or a field of another name holds, which is how an instance's own `home.env` reaches most code, and a write in a naming file through a key held in a local. |
| `teamai/mock-source` | A `vi.mock` or `vi.doMock` of a module that only re-exports another one, which leaves every module importing the original unmocked. `vi.mock('../utils/logger.js', ...)` becomes `vi.mock('@teamai/tool-core/log', ...)`, because `src/utils/logger.ts` is `export * from '@teamai/tool-core/log'` and code in `packages/*` imports the package. Imports of the old path still get the mock. Any file under lint is checked; a barrel over several modules is not reported. |
| `teamai/uncached-entry` | An import of anything but a `node:` module or another file in `UNCACHED` from what `src/bin.ts` loads before the CLI bundle: every hook loads it, and the hook fast path exits on it alone (#1788). A new file there joins `UNCACHED` once it imports nothing else. Type-only imports are exempt. |
| `teamai/no-low-value-comments` | A comment that only repeats the name below it (`// State` above `const state`), commented-out code, a `TODO` with no issue, or a JSDoc type in TypeScript. Issue numbers and `// ───` dividers stay allowed. |
| `teamai/suppression-reason` | An `oxlint-disable` / `eslint-disable`, or a `@ts-expect-error` / `@ts-ignore` / `@ts-nocheck`, that says nothing about why. End it with `-- reason` (after a TypeScript directive, just the reason), or put the reason in a comment on the line above. |

Production-scoped rules check `src/` and `packages/*/src/`, outside `src/__tests__/` and `*.test.ts`. `teamai/shipped-tool-ids`, `teamai/configured-tool-paths` and `teamai/tool-home-env` also check `scripts/`, outside its tests: the documentation generator and the verify world run the product's own modules.

The plugin also carries the generic rules of anti-slop, vendored in `anti-slop/` (`anti-slop/UPSTREAM.md` says from where). They report as `teamai/<rule>` and hold production code only; tests are exempt. Each message names its fix, for example:

| You wrote | `npm run lint` says | Fix |
|---|---|---|
| `typeof payload.session_id === 'string'` on parsed hook JSON | `` teamai(no-runtime-typeof): A `typeof` check narrows a representation without establishing its contract. `` | Parse the payload with a zod schema where it comes in, then read `parsed.data.session_id`. |
| `return name as ToolId;` | `` teamai(require-safety-comment-for-type-assertion): This type assertion has no `SAFETY:` justification. `` | Drop the cast, or write the check that makes it true on the line above: `// SAFETY: the includes() check above proves name is a ToolId.` |
| `const body: Record<string, unknown> = { name, private: true }` | `` teamai(no-known-value-widening): The explicit open dictionary type on binding `body` discards known type evidence. `` | `const body = { name, private: true }` |
| `items.filter((item) => item.active).map((item) => item.id)` | `` teamai(no-array-filter-map): Avoid consecutive array `filter` and `map` passes. `` | `items.flatMap((item) => (item.active ? [item.id] : []))` |

## Add a rule

1. Write `rules/<rule>.js` with `defineRule`, register it in `index.js`, and add its row to the table above, which `npm run lint` checks. oxlint imports these files with plain Node, so they are JavaScript (`npm run lint` runs on Node 20 in CI); `npm run typecheck` checks them through their JSDoc types.
2. Turn it on in `.oxlintrc.json`: `"teamai/<rule>": "error"`.
3. Test it with real oxlint in `rules/<rule>.test.ts`:

```ts
import { describe, expect } from 'vitest';
import { ruleHarness } from '../test/harness.ts';

const rule = ruleHarness('teamai/remove-delivered', { filename: 'src/pull.ts' });

const bareRemove = `import { remove } from './utils/fs.js';\nawait remove(dir);`;

describe('teamai/remove-delivered', () => {
  rule.invalid('reports remove from src/utils/fs', bareRemove, (output) => {
    expect(output).toContain('removeDelivered');
  });
  rule.valid('allows removeDelivered', `await removeDelivered(ledger, dir);`);
  rule.valid('only in pull\'s files', bareRemove, { filename: 'src/push.ts' });
});
```

`filename` is where the fixture sits, relative to the repository root, so a rule scoped to some files can be tested in and out of them. Shared AST helpers go in `utils.js`. All cases in one harness invocation run through one oxlint subprocess, with diagnostics checked against each fixture and its intended rule.

A line that must break a rule carries the reason:

```ts
// oxlint-disable-next-line teamai/remove-delivered -- a team-repo file, which pull never records
await remove(teamFile);
```

`npx vitest run oxlint-plugin-teamai` runs the rule tests; `npm run typecheck` checks the plugin.
